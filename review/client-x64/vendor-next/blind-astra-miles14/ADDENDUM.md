## Corrections and evidence boundaries

**High evidentiary priority — universal suspension is unsupported.** Observed: `Mss.h:3825–3828` describes the startup application's thread being suspended by callback threads. But the Windows-specific preference block begins at `1559`; `1597–1598` defines `AIL_LOCK_PROTECTION=18` and `DEFAULT_ALP=NO`, explicitly commenting that foreground suspension is not the default. `1600–1601` separately defaults per-call mutex protection to YES. Those are different controls, and neither should be conflated with the game's explicit `AIL_lock`/`AIL_unlock` interval.

Observed: `Audio.cpp:1289–1297` calls startup, registers file callbacks and queries mixer channels. The only `AIL_set_preference` calls found in the inspected engine/game C++ and header sources are `Audio.cpp:5118,5125`, both changing `DIG_DS_MIX_FRAGMENT_CNT`. I found no game-source request enabling lock protection. Inference: the documented default is a strong reason not to assume automatic suspension in this client's normal configuration. Limits: header defaults are not a runtime reading of the loaded DLL, and absence of a game call does not establish all vendor/plugin/internal behavior. The reported SuspendThread/ResumeThread imports establish available implementation machinery, not that this preference or any particular suspension path executes.

Disconfirming measurement: record `AIL_get_preference(AIL_LOCK_PROTECTION)` and `AIL_get_preference(AIL_MUTEX_PROTECTION)` in the original client's actual initialized session and relevant lifecycle stages; identify the exact loaded DLL. If asserting suspension, trace actual suspend/resume calls and their target thread during the relevant callbacks. A zero preference alone would not prove no other suspension path exists. Do not add cross-process suspension to the adapter just to reproduce an unverified assumption.

**High integration gate, unchanged — callback causality still requires an engine-level design.** Observed: starts run inside the game lock interval (`Audio.cpp:2320–2337`); EOS mutates the sample map's state and invokes game sound policy (`4730–4743`); file callbacks use TreeFile and game-owned file state (`3939–4098`, examined in the opening). These dependencies do not require universal foreground suspension to be difficult. If the original callback actually runs concurrently, arbitrarily moving all callbacks to the main thread is itself a semantic change; if it is serialized by vendor synchronization, a generic asynchronous queue does not prove preservation either. The source does not settle the dynamic ordering.

Scope/disconfirming test: the original vertical-slice gate remains the next architectural discriminator. Trace which thread runs each callback, what lock/admission state is active, which caller is awaiting a reply, and which alter epoch observes the state transition. Cover reverse IO during a pending call and EOS with no client request outstanding. Compare the original game policy with the bridged policy. Do not demand reproduction of an unmeasured suspension mechanism; demand evidence of the observable ordering and progress the game actually relies on.

**Medium investigation priority — FPU differences are plausible but unmeasured at the decisive boundary.** Observed: `Os.cpp:243–244` installs the foundation FPU policy; `Os.cpp:705` updates it. `FloatingPointUnit.cpp:67–126` chooses x87 24-bit precision for Win32, nearest rounding and configurable exception masks; x64 instead uses fixed-by-type precision and MXCSR. `131–139` restores the configured control state when it differs. Thus the real engine has explicit FPU policy that the standalone vendor probe does not reproduce merely by using the same DLL. The frozen controlled sample log's callback at line 300 records `cw=027f` and `mx=00001f80`, but that is the standalone probe, not an SWG-to-Miles boundary trace.

Inference/scope: keeping the same DLL does not by itself prove identical floating-point inputs or inherited control state on the host dispatch thread. Conversely, a different recorded control word is not proof of changed output: vendor code may normalize state, use another instruction path, or perform the relevant work on its own worker. Callback suspension says nothing by itself about transfer of FPU state between threads. No audible, numerical, exception, or gameplay divergence has been measured here.

Disconfirming test: extend the engine-level comparison with non-mutating observations of x87 control/status and MXCSR immediately before/after representative Miles calls and at callback entry/exit, identified by thread and phase. Trace the original Win32 policy, the x86 host dispatch lane and vendor workers, and the x64 policy side separately. Associate differences with actual return values, decoded/mixed output and engine transitions. Do not copy raw x87 control-word bits into MXCSR or reset exception state globally as a speculative fix. A confirmed relevant state difference should produce a narrowly specified host/callback context contract, followed by output comparison.
