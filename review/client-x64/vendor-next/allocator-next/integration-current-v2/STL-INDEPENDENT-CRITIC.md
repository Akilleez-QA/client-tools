2026-09-30. Read-only review of client-stl-integration candidate at085f77cc7, bundled STLport4.5.3 configuration, real native directive census and evaluated metadata. No production or VM edits.

**Correction:** the earlier inference that there were no STLport autoload directives was false. Absence of an assumed macro is not evidence about compiled COFF directives. The actual Release census contains63 archives,55 with `/DEFAULTLIB:stlport_vc71_static.lib`; this is the sole STLport name in that census. The three recorded Debug archives also request that ordinary static name, alongside debug CRT directives. `stl_select_lib.h` emits the pragma when own iostreams are enabled and neither __BUILDING_STLPORT nor _STLP_DONT_FORCE_MSVC_LIB_NAME suppresses it. The v120 compiler still selects basename vc71 through the old header's _MSC_VER>=1310 test.

A project named Debug, /MTd and `_DEBUG` do **not** imply `_STLP_DEBUG`. The latter changes container/debug implementation names and must agree with the provider. `_DEBUG` selects a separate `_debug` library only if `_STLP_USE_DEBUG_LIB` is also defined. Current provider builder uses repository33TUs, /MT or /MTd, /Zc:wchar_t-, and no _STLP_DEBUG; this matches the observed ordinary static requests. Naming the file stlport.lib is immaterial if the actual binary ABI matches; merely renaming an incompatible binary would not fix it.

## Three strongest risks and checks

1. **Partial consumer census can miss an incompatible mode.** Finish the Debug archive census and inspect final executable objects, not only sharedFoundation/clientGame/sharedNetworkMessages. Record actual macro/CRT/wchar settings and provider symbols for real uses (strings, node allocator and iostreams). Explicit stale stldebug input does not establish STL-debug consumers. Conversely suppressing that input must not hide an actual _STLP_DEBUG object. Namespace and decorated symbol checks are stronger than configuration names; successful complete linking is still required.

2. **Explicit inputs and autolink are separate routes.** The candidate removes the one known explicit `stlport_vc71_stldebug_static.lib;` and suppresses only observed default `stlport_vc71_static.lib`, providing the matching generated path. This is appropriately narrow, but String.Replace is substring matching, not a general semicolon token parser. For current metadata verify exactly one full entry disappears, one provider appears, all other input tokens/order remain identical, and both Win32 configurations remain byte-identical. Run /VERBOSE:LIB with old providers unavailable to prove the generated provider resolves symbols and no stale x86 archive is silently selected. Unresolved unrelated vendor symbols do not invalidate a successful bounded STLport resolution, but cannot be called a successful product link.

3. **Property factoring changes build execution, not just names.** Moving the dependency target into the shared sheet must retain renderer validation, execute the genuine builder before Link, and use configuration/platform-separated paths. SwgClient now requires the pinned JPEG archive as well because the builder produces both libraries; this is an explicit additional offline prerequisite, not a compiler/runtime ABI change. Native evaluated properties16/16 establish import evaluation, not target execution or provider selection. Capture a real target invocation/incremental rerun, selected manifest identities and actual provider path. Existing single-output ownership/cache limits remain; no new concurrency guarantee follows from factoring.

The candidate leaves renderer consumer macro suppression as before and does not globally enable STL-debug or alter CRT policy. Source review found no new ABI-policy mismatch. Win32 unchanged claims should be based on the actual evaluation comparison, then the normal regression build, not only the x64-conditioned import text. Full Debug census and exact native link evidence remain the key acceptance gates.
