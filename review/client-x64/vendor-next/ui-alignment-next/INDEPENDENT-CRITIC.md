# Independent bounded UI pool review

2026-09-30, read-only production review. Reviewed native-layout report plus actual UiMemoryBlockManager.cpp/.h and macro consumers in client-build-next. No old misaligned objects executed, no production edits.

**Verdict:** changing only `s_alignment` from4 to `sizeof(size_t)` is a defensible repair of the demonstrated current x64 eight-byte alignment bug. It is not a general16-byte-aligned replacement for malloc/new, and must not be described as one. Changing only alignment to16 also cannot provide that stronger contract: the user pointer still adds an eight-byte header. A full16-byte scheme needs a padded header span and matching free/header lookup, broadening this repair without a demonstrated current16-byte consumer.

The actual manager owners are UIBaseObject (8MiB pools), UIWidgetRectangleStyles (1MiB), UIPacking::LocationInfo and SizeInfo (2MiB each), and UIWidgetBoundaries (1MiB). UIBaseObject's inherited class operator new covers UIButton/UIPage/UIText and client subclasses. The class macro also defines placement new (passes the caller address through; no pool guarantee) and scalar delete; there is no array-new override. Repository `allocMem(` search finds no direct variable-size external caller beyond that macro.

A scoped scan of ui, clientUserInterface and swgClientUserInterface found no alignas, __declspec(align), __m128/__m256, SLIST_ENTRY or MEMORY_ALLOCATION_ALIGNMENT use. Concrete external subclasses include CuiWidgetGraph, CuiWidgetGroundRadar, CuiWidget3dObjectViewer/ListViewer, CuiGenericRenderer, CuiWorkspaceIcon/GlassPane, radar pane classes and SwgCuiAllTargets::MyRenderer. Deprecated browser/TCG wrapper subclasses are also present, but not grounds for resurrecting them. This scan plus three native class layouts supports the bounded repair; it is not a compiler proof of every transitive member or future subclass. The explicitly16-aligned PaddedVector found elsewhere is local to SoftwareBlendSkeletalShaderPrimitive, not an identified UI member.

**Acceptance:** retain native compile-only layout evidence. Run the corrected actual manager with small mixed sizes and repeated free/reuse, checking both raw size-header and returned pointer alignment, distinct live ranges, stored lengths and basic canaries. Keep the same Win32 arithmetic and pool policy. Native class-layout checks should include the four other pool families and representative externally derived widget types if affordable. Runtime tests should not instantiate old misaligned objects; the negative control is arithmetic. `independent-arithmetic.json` checks sizes1..4096 at four successive offsets: old x64 fails4096 positions; candidate fails0; Win32 formulas identical throughout. For Release UIButton496, old user offsets8/516/1024 violate8 alignment at516; candidate8/520/1032 satisfy8, but all remain8 modulo16. Thus a test expecting16 must deliberately fail for the narrow candidate.

**Separate size-key proposal:** `hash_multimap<int,void*>` should use size_t to retain the actual size identity. find(size) and insertion of stored size_t currently narrow both sides; x64 values separated by2^32 can alias. Ordinary fixed class sizes do not establish a reachable huge-allocation scenario. A tiny map-only test with distinct keys1 and2^32+1 can discriminate key identity without allocating either size, but must be labelled a map/helper test, not allocator oversized-request coverage. Win32 size_t changes signed key representation/hash details for the upper half even though width remains32; ordinary positive small sizes are unchanged. MemoryMap is a private heap object and manager holds only a pointer, so public manager/object sizes need not change; rebuild the UI implementation rather than mix old/new private-map TUs. This change alone does not fix requestedSize overflow, impossible-pool recursion, malloc failure or Debug byte-counter overflow.

Microsoft primary references (checked2026-09-30): [x64 ABI types](https://learn.microsoft.com/en-us/cpp/build/x64-software-conventions) distinguishes pointer8 from __m128 alignment16; [allocator alignment warning](https://devblogs.microsoft.com/oldnewthing/20121115-00/?p=6083) explains why a general Windows allocator must preserve16 alignment for SLIST_ENTRY. Those stronger generic requirements warrant an explicit limitation here, not an unsupported claim that every existing UI class needs16. Win32 native evidence remains4 for the measured classes, and the proposed constant remains4 there.
