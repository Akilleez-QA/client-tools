# Primary research record

Retrieved 2026-09-30. These sources describe supported mechanisms and candidate implementations, not equivalence to the installed SWG runtime. Local source and actual-version measurements remain the authority for local behavior. URLs were opened; unsuccessful fetches are excluded from load-bearing claims.

| Question / search | Source and evidence family | Decision-relevant observation and limit |
| --- | --- | --- |
| Windows 32/64 DLL interoperability | [Microsoft process interoperability](https://learn.microsoft.com/en-us/windows/win32/winprog64/process-interoperability), updated 2019-08-23 | Ordinary mixed-architecture DLL loading is unsupported; out-of-process RPC/COM is supported. Does not prove latency or callback equivalence for SWG. |
| Cross-process frame transport | [Microsoft shared memory](https://learn.microsoft.com/en-us/windows/win32/memory/creating-named-shared-memory), updated 2024-07-30 | Mapped sections permit shared data. Pointers/ownership and synchronization still need a protocol. The sample's Global namespace privilege is not a requirement to use a private same-session mapping. |
| Callback reentrancy / blocking | [Microsoft pipe I/O](https://learn.microsoft.com/en-us/windows/win32/ipc/synchronous-and-overlapped-input-and-output), updated 2021-01-07 | Synchronous waits can block indefinitely; overlapped I/O permits concurrency. Neither automatically reproduces synchronous SDK getters or prevents engine-level deadlocks. |
| 32-bit helper memory ceiling | [Microsoft virtual address space](https://learn.microsoft.com/en-us/windows/win32/winprog64/virtual-address-space) | A 32-bit helper remains address-space limited; a 64-bit main process has a separate larger address space. Exact helper capacity depends on its executable configuration and OS. |
| Bink compatible x64 availability | [RAD SDK downloads](https://www.radgametools.com/bnkdown.htm) and [development history](https://www.radgametools.com/bnkhist.htm), current entry 2026.06 | SDK distribution is for licensed customers. History records changes in audio, seeking and synchronization, including a substantial sound-provider rewrite. Newest SDK is not evidence of unchanged historical behavior. |
| Existing vendor use of helper architecture | [RAD Bink history](https://www.radgametools.com/bnkhist.htm), January 2019 compressor entry | Its 64-bit compressor used a 32-bit process for legacy importers. This demonstrates an architecture in an offline tool, not real-time SWG fidelity. |
| Independent Bink decoder | [FFmpeg n8.0 Bink video source](https://raw.githubusercontent.com/FFmpeg/FFmpeg/n8.0/libavcodec/bink.c), [Bink audio source](https://www.ffmpeg.org/doxygen/8.0/binkaudio_8c_source.html) | Real decoder implementations exist. Asset-version support, color conversion, PCM rounding and playback scheduling must be compared with the original runtime. |
| Decoder distribution | [FFmpeg licensing](https://ffmpeg.org/legal.html) | Configuration and optional components affect license obligations; choose an explicit build. This is not a legal determination about SWG or existing assets. |
| Vivox upgrade rather than bridge | [Vivox V4-to-V5 guide](https://docs.vivox.com/v5/general/unreal/5_21_0/en-us/developer-guide-supplement/Vivox_V4toV5_Guide.pdf), [current Core docs](https://docs.unity.com/en-us/vivox-core) | Native voice SDK family continues, but migration changes authentication and APIs and removes some earlier behavior. Guide is V4-to-V5, while SWG headers identify an older generation; it establishes migration risk, not a complete local upgrade recipe. |
| Current voice provisioning | [Vivox Core access tokens](https://docs.unity.com/en-us/vivox-core/access-token-guide/access-token-guide-toc) | Current privileged operations use tokens signed with service credentials. Original SWG account/password and channel provisioning cannot be assumed interchangeable. No live service was contacted or tested. |

The research challenges both easy answers: native x64 SDKs may change behavior; original-runtime helpers may change timing. No source establishes literal 100% fidelity for either route. Miles/JUCE/OpenAL/miniaudio and the secondary-vendor research are recorded in their separate dossiers.

## 2026-09-30 continuation: original vendor process boundary

Queries: `site.learn.microsoft.com process interoperability 32 bit process 64 bit DLL IPC`; `site.radgametools.com miles 64 bit audio system callbacks`. Primary Microsoft IPC documentation (https://learn.microsoft.com/en-us/windows/win32/winprog64/interprocess-communication) supports cross-bitness process communication and prohibits directly loading the opposite-bitness DLL. It does not establish callback timing, pointer validity, game fidelity or acceptance of this proposed bridge. RAD product/history pages (https://www.radgametools.com/miles.htm and https://www.radgametools.com/msshist.htm) establish native64 support exists in Miles history, not access to a matching licensed legacy SDK or identical mixer/codec behavior. Existing measured original-runtime experiments remain more direct evidence for the local legacy artifact. This refresh supports continued already-selected investigation; no production backend decision or fidelity threshold is made.
