# Disposable Bink feasibility result

**The original Bink DLL loads in a real v120 x86 process, and a real v120 x64 driver can launch that process and receive verified framed metadata. Movie decode and FFmpeg equivalence remain untested because no original movie was found in the supplied installation. This does not satisfy the 100% original-experience requirement.**

Original runtime: `binkw32.dll`, PE32/i386, version 1.9c, RAD Game Tools, Inc.; PE timestamp 2008-01-15 23:57:01. SHA-256 `e67e0319f9929c024a6d0757de50c65257f686f6711cb0efb7ad53afc3405dd4`. Imports: USER32.dll, GDI32.dll, KERNEL32.dll, WINMM.dll; complete functions/exports in `logs/runtime-pe.txt`. No missing-import/platform failure occurred. Supplied header identifies Bink 1.9c (2008-01-15). Probe resolves actual DLL functions dynamically, using supplied declarations and structures; no stubs.

Asset search: 209 top-level TREs inspected. 72 supported 0004/0005 archives yielded no `.bik` entry; metadata reads totaled 5,373,439 bytes. Remaining 137 report version 0006 and zero entries and were rejected rather than interpreting an unsupported format. Recursive loose-file search found no `.bik`, `.bk2`, or `.smk`. Broader bounded name-block inspection also found no movie/video paths. The independent `../tre-media-inventory.json` contains no Bink movie entries; it was read only. This establishes absence in inspected locations/formats, not absence in every possible encoding or installation. No movie hash/container/frame/audio results can honestly be supplied.

`probe.cpp` compiled with VS12/v120, /MT and /MACHINE:X86. It includes the bounded CPU decode path (32 frames, samples 1/8/16/32, BINKSURFACE32A|BINKCOPYALL) and track-zero extraction using BINKTRACK.MaxSize. These decode paths have only compiled, not run: track-call sequencing, pixel layout and audio semantics remain unvalidated. No audio system is initialized. No sound playback or A/V fidelity is claimed.

`driver.cpp` compiled /MACHINE:X64. Two final runs returned a 116-byte payload with child exit 0 and matching FNV-1a transport checksum `478950ba1e591338`; Python independently validated framing, checksum, x86 metadata and repeated SHA-256 `fa2b4ae80efc784bbe343f9c0104c707ba5755b7d2ffaae4330a52cd6073d32a`. PE machine values were independently read: probe 0x14c, driver 0x8664. This demonstrates process launch and metadata transport only, not decoded-frame transport, performance, audio/video timing or production suitability. Initial race/newline-translation failures and final passing logs are preserved.

Installed FFmpeg exposes binkvideo, binkaudio_dct and binkaudio_rdft. Version/build information is retained. Oracle was written before execution: BGRA, explicit BT.601 limited-to-full conversion, alpha included, preserve all discrepancies. The comparator command is saved but was not run without a movie. There are no matching or mismatching pixel claims.

Source implications: BinkDLL.cpp binds 32-bit decorated exports; BinkTreeFileIO.cpp casts AbstractFile pointers into U32 handles. BinkVideo.cpp connects Miles, custom TreeFile I/O and Direct3D texture/backbuffer drawing (including 32A/565/5551 surfaces), frame scheduling and device lifecycle. A helper requires explicit transport and preservation of these behaviors. A native replacement requires authentic asset coverage and acceptance of video conversion, audio, synchronization, seeking/looping, skips, scaling, device loss and shutdown. Neither route is approved by this experiment; no SDK feature was removed and no production source was changed.

Next evidence needed: a locally available original movie and its installation provenance. Reuse the predeclared oracle without choosing conversion parameters to force equality. A positive sample comparison would still not establish whole-game experience equivalence.

No game launched; no installation edits, credentials copied, external uploads, commits or pushes. All writes are within the two authorized probe directories.
