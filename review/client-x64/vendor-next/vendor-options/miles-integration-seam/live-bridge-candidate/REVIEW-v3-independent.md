# Independent bounded review of the v3 repair candidate

Reviewed 2026-09-30 from source and retained raw evidence only. No chat or peer reports were consulted. No vendor media, native executable, fault workload, build, or runtime was executed. Only this review file was written. This is component qualification, not playback or full-client fidelity certification.

**Disposition:** the four targeted repairs are supported within the limits below. The genuine Debug/Release logs and the valid-input L/R mutation support the reported 21-request no-playback observations and normal teardown. There is no blocking contradiction in those bounded claims. Complete detection of callback faults during cancellation, an aggregate memory bound, and a cryptographically complete source-to-build-to-runtime provenance chain are not established.

## Confirmed repairs

1. **Staged payload copying is reduced.** `../host-candidate/retained_buffers.cpp:17–42` copies bytes into a local candidate, inserts an empty entry, then swaps same-default-allocator vector storage into the entry. Published accounting and the output token follow the nonallocating swap. Existing retained entries, active token, accounting and caller output survive allocation failure before insertion by source reasoning; the global token sequence can advance before a failed map allocation. This is not an assertion that every process-global state is unchanged.

   The four `evidence-v3b/*/payload-run.log` and old-control results discriminate one versus three exact 9,020-byte allocations. The four corrected `evidence-payload-v3c/*/payload[-old]-run.log` pairs, decoded as UTF-16, report a 9,020-byte published view for both variants. The only current C++ mismatch against the v3b source manifest is the documented two-line change evaluating `view` before the short-circuit expression. The old implementation's zero printed view in v3b was diagnostic, not evidence of zero storage. All four v3b retained suites report 41 ownership checks.

   `BufferUpload::copySealed`, the bind path and `stage` support three simultaneous logical full-image stores at bind: upload, sealed temporary, and candidate/retained storage. That is 27,060 image bytes, excluding suffix and other storage. Neither this accounting nor an exact-size `operator new` counter measures RSS, vector capacity, total live allocation, framing storage, allocator overhead or SDK allocation. Allocation-fault exception behavior was not exercised.

2. **Rejected operations do not incorrectly drain or consume admission ordinals.** `admission.h:14–29` advances `lastAdmitted` only after successful coordinator admission, completes admission before considering drain, and drains only for successful shutdown. `bridge.cpp:35–53` validates fields and prerequisites before invoking the real shutdown and returning success. In Draining, only SessionClose uses cleanup admission. Rejected backend shutdown is nevertheless an admitted/completed operation and legitimately consumes that admission ordinal; a rejection by admission itself does not. The synthetic test explicitly covers both distinctions and a subsequent SessionClose. The retained initial v3 failure says `FAIL explicit session close cleanup`; v3b's four repair logs each report 25 passing checks using the same helper as the bridge. Genuine runs exercise successful shutdown, not the synthetic rejected-shutdown cases.

3. **An observed idle-channel fault cannot be hidden by a ready command.** `common.h:25–42` pumps both endpoints and checks the callback endpoint before taking the command frame. The real-pipe controls supply a ready reply with callback PeerClosed or InvalidLength and require failure, including failure when draining an already-faulted pair. Only PeerClosed is exempted at the final close boundary; corruption in the control is still rejected. The actual client validates reply kind, request, opcode, lane, causal/lease fields and transport status after receive. These source paths and all four 25-check logs support the repair to the previously observed-fault case.

4. **The pre-assignment suspended child has an owner.** `common.h:49–82` initializes ownership before CreateProcess, terminates/waits for a live child on cleanup, then closes thread/process/job handles. The production controller constructs that owner before create/assign/resume. `repair-tests.cpp:60–73` uses the same owner, a suspended benign self-child, an invalid job handle, and a duplicate observation handle. It checks assignment rejection, termination exit 90 and closure of all three owner handles. All four configurations pass. This directly qualifies assignment failure before resume; failure of every other launch/resume API or termination itself was not tested.

## Genuine and negative evidence

Both `evidence-v3b/runtime/{Debug,Release}-host.log` contain requests 1–21, genuine successful bind, 204/407-ms duration observations, 22050/11025 rates and 0.25/0.75 volume values. Request 18 rejects a retired sample token with transport 2. Sample release, buffer release, original shutdown, SessionClose and the host PASS line occur in order, with no emergency-cleanup marker. Controller logs pass 21 requests and recorded return codes are zero. Controller source requires host exit zero before printing success.

The mutation source changes the dispatcher's L/R argument order while preserving the direct control. Its controller explicitly expects mismatch status 5 and swapped output values, then continues normal teardown before returning 1. Both mutation host logs show status 5 at request 12 and all 21 requests, sample release, shutdown and host PASS. Both controllers print the discrimination and completed-teardown markers. The negative is a valid-input semantic control, not malformed media or an abrupt failure accepted as success.

The runner checks the original DLL and fixture digests, copies them into a private prefix, and logs the loaded DLL path. Results record matching before/after default audio settings; runner source unloads the owned sink. This review inspected those records and code, not a live process or audio device.

## Evidence binding and remaining defects/limits

- Recomputed current source hashes match all 37 v3b manifest entries except the disclosed payload diagnostic revision. All 37 archived `source-v3b.tar` entries match that manifest. The native build record has 62 source hashes, and its current-source mismatch is also only the payload diagnostic. All 62 recorded mutation source hashes match the retained mutation tree. Build commands use VS12/v120, Debug `/MTd /Od` or Release `/MT /O2`, and `/W4 /WX`; raw matrix records report success.
- Recomputed hashes of all eight retained positive/mutation host/controller executables match their respective runtime `host_sha256` and `controller_sha256` records. The v3 runner selects `native-v3b`; mutation runtime uses its separate binaries. Thus runtime identities and retained source versions are internally consistent. **Provenance limitation:** native build JSON records source hashes but no output executable hashes; runtime JSON hashes current C++ files after execution and omits headers/dependencies. The curated text packet does not independently prove an unbroken source-to-binary association. This is ordinary recorded build/run evidence, not a reproducible-build or signed build attestation. Preserve the limitation or add build-time output hashes linked to the source manifest before claiming stronger binding. v3c has build/run logs but no separate source/exit-code manifest; old exit 1 is directly recorded in v3b, while v3c directly corroborates the corrected printed observation.
- **Drain limitation:** `Endpoint::drain` calls `cancel`, which changes Open to Stopping; `Endpoint::collect` records errors/parses completed reads only while Open (`../pipe-transport-candidate/endpoint.cpp:66–75,102–116`). A fault or malformed bytes first observed after that transition can therefore be discarded as cancellation cleanup. The added pre/post checks preserve previously classified faults; they do not establish a cross-channel frontier or detect every fault arising during drain. The current controls do not test that race. Wording such as “corruption never gains an exemption” must remain limited to corruption actually classified before cancellation. A general callback-close protocol remains unqualified.
- Host server-PID validation is conditional and only on the command pipe. Controller validation covers the child PID on both pipes. Full mutual authentication is not established.
- No evidence here qualifies playback, callback registration/execution, streams, engine teardown, scheduling fairness, crash recovery, real-device behavior, malformed media or full-client fidelity. The retracted 32-KiB aggregate-memory claim remains unsupported. No source/runtime changes are recommended as a prerequisite for retaining these narrowly stated component observations; broader production claims require additional design and qualification.
