## Specific checks

- **Synchronous partial I/O does not strand the loop.** `candidate/client-runtime53/client_file_runtime.cpp:128-156` pumps on every iteration and always waits at most 2 ms for another iteration. `candidate/pipe-transport-candidate/endpoint.cpp:99-100` may stop after four synchronous completions without leaving a pending event;53 still pumps again. It has neither host50's earlier no-event fatal condition nor an infinite idle wait that strands partial input. The fixed polling latency is a performance choice, not an observed deadlock. Replies queued at runtime line149 begin pumping on the next bounded iteration.
- **Admission precedes the caller's permitted send.** Runtime `post` lines62-70 holds the single caller mutex, publishes the shared ticket under slotMutex, and waits for done/terminal. Publish lines99-106 calls mapper/coordinator admission before completing that ticket. `complete` lines72-75 releases the slot, writes result, and signals done. Ticket shared ownership covers caller/owner handoff; successful return cannot precede admission. Wire monotonicity and local ordinal monotonicity are separate. The upcoming LiveChannel still must obey this API ordering; no command send implementation exists here to verify.
- **Forward return remains joined to causal consumption.** Runtime lines108-112 and78-84 keep the return ticket pending in ReturnedWaiting and complete only after mapper settles and consumes it. Mapper lines28-40/130/143-149 settle through Coordinator::completeAdmission, whose causalPending check prevents early release. The next loop iteration revisits the pending return after incoming ACK processing. Prepared startup work uses the same coordinator and preserves its ordinal; preparation refuses an active admission at runtime88.
- **ACK dispatch and queued state agree with the protocol contract.** Runtime line149 first copies the reply into Endpoint through send(), then marks its mapper row queued. Both occur on the sole control thread before another receiveControl invocation. Mapper lines65-71 select ACK before new-request monotonic validation; full expected-frame validation precedes acknowledgeConsumed. Mapper143-148 requires queued, lets owner acknowledge, and removes the reverse row once. Duplicate/unknown/early ACK is terminal. Queue acceptance is explicitly not proof of peer consumption; only the authenticated exact ACK supplies that observation. Endpoint allocation failure leaves the real owner/row retained, not a fabricated read result.
- **Actual worker readiness is checked.** Runtime90-96 retains the supplied table, publishes worker pointer before start, requires Started, then builds actual FileSessionContext/owner/mapper. External EngineFileWorker.cpp70-91 waits for ready after actual engine Thread startup; run118-120 signals that readiness. This supports intended ordering, not execution proof for the new control thread. Runtime does not substitute portable_job. It never waits on an admitted job: owner.poll uses FileInvocationJob's completion event; job.cpp enqueue publishes PendingContext ownership before submit and the job retains Invocation/table/context.
- **Retained failure ownership is concrete.** State fields38-47 retain the current ticket, engine lifetime, worker, context, owner and mapper. Runtime158-162 enters terminal state and retains the issuing control thread while draining cancellation. Partial prepare failure retains its worker; a still-posted preparation ticket retains original callback pointers/lifetime even if local selected-services construction unwinds before context publication. Successfully prepared context contains the retained selected table. Completed file records remain inside the retained owner even after their operations have been ACKed. This is deliberate lifetime retention, not cleanup or recovery.
- **Reentry boundary is still a required outer integration.** Actual Invocation installs guard47 around engine callbacks at file_channel.cpp143-147. Runtime synchronous posting itself does not enforce the public forward guard. As PLAN states, calling returned/publish from an executing callback can deadlock the single worker/command chain. The real facade must run its existing guard before reaching this runtime. Do not claim that merely including guard source completes that boundary.
