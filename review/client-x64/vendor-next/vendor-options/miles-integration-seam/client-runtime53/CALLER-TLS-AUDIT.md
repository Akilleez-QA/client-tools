# Caller-side engine TLS audit for runtime53

Source-only audit against `/home/akilleez/Work/swg-source/client-build-next` at the supplied unchanged product revision, and frozen runtime53 manifest `19d7d3376d2a8ea73fc7282c7c0bfe75d559d95b9845785119e2eff5ede00aad`. No native/portable compile, runtime, allocator workload or product/source change. This report is the sole new audit artifact.

## Conclusion

The worker's installed TLS does **not** protect runtime53's caller-side engine work. However, the actual inspected create/start/submit success paths do **not** contain an unconditional `PerThreadData` dereference or require a nonnull `Thread::getCurrentThread()`. Therefore “every call from the raw control thread necessarily crashes for missing TLS” is not supported by source.

The wider diagnostic/error contract is not equivalent to an engine-initialized thread: reporting without TLS selects shared static flags under an explicit single-threaded assumption, and fatal handling skips the caller's per-thread exit chain. Optional allocation profiling additionally mutates shared profiler state regardless of TLS. **Do not classify missing caller TLS as a defect or add a TLS mechanism solely to fix these inspected normal calls.** The bounded success path permits a foreign thread once global engine setup/lifetime is established. Before operational wiring, state the supported diagnostic profile and fatal policy. A small current-thread TLS shim is an optional way to obtain per-thread Report/ExitChain behavior if that is actually required; it does not make allocation profiling thread-safe and introduces installation/removal ownership of its own. Replacing the control thread with another engine Thread is likewise not justified by this call chain.

## Optional profiler and free-path audit

- MemoryManager.cpp:270 declares `ms_debugProfileAllocate` at static storage (initially false); line838 registers it as `SharedMemoryManager/profileAllocate`. In `_DEBUG`, allocation checks this flag and enters the block at1219–1221; its paired leave is1376–1378. Enter is **before** allocator critical-section entry1242; leave is **after** allocator unlock1372. Even holding the allocator's lock would not serialize unrelated main-thread profiler blocks.
- Profiler.h:134–143 routes block enter/leave to Profiler; macros210–214 enable it in `_DEBUG`. Profiler.cpp:813–826 obtains a timer and calls enterWithTime/leaveWithTime. The latter operate on namespace-global stack/vector/depth state: declarations90–94,108–109,122; mutations705–761 and768–807. No PerThreadData, Thread identity selection or lock protects that state in those functions. A control-thread allocation profiled concurrently with another profiler thread can therefore interleave stack/vector mutations and hit mismatched-block/underflow diagnostics. This is an optional profiler concurrency limitation **with or without caller TLS**, not evidence that threadInstall fixes it. No runtime interleaving was exercised.
- There is **no allocation-profile block enter/leave counterpart in MemoryManager::free** in this source. Free1455 onward checks global install/pointer, optionally verifies guards1466–1468, reports pointer1471, enters allocator lock1475, performs bookkeeping/coalescing, and can report/fatal on corrupt guards/bad deletes. It has the Report/fatal considerations already listed; it does not acquire per-thread profiler state. The matching LEAVE requested for allocation is1378, not a free operation.
- Default-false allocation profiling removes that specific optional path, but does not prove all engine debugging safe. Report's static fallback can collide if multiple **uninstalled** threads report; properly TLS-installed reporters use their own flags and do not inherently race with that fallback. The audit does not establish that53 necessarily has two uninstalled reporters. Conversely, optional debug reporting/errors must not be presented as TLS-equivalent merely because normal queueing works.

## Bounded recommendation and optional boundary

First retain the existing plain worker interface and record the caller contract: global engine setup precedes this foreign thread's engine calls; setup remains alive; no file callback runs on the control thread; allocation profiling's cross-thread global-state limitation is not certified. A native source compile can proceed without asserting runtime readiness. No TLS implementation is justified as a mandatory repair from this audit alone.

If the integration explicitly requires per-thread Report/ExitChain semantics on its control thread, the smallest optional boundary is:

1. Keep the modern control thread and Endpoint ownership unchanged. Add an engine-compiled private plain header/TU exposing current-thread entry and eventual exit, with no STL objects or engine exceptions crossing the boundary. The outer root must prove Foundation/PerThreadData/MemoryManager installation before launch; do not trigger global subsystem installation from this shim.
2. On this newly created thread, before worker.create/start/submit, enter PerThreadData with the correct `isNewThread=true` contract. `PerThreadData.cpp:175–208` documents this path and sets its own slot. It necessarily allocates Data and a Gate **before** publishing TLS; this is the engine's existing bootstrap pattern, so adding the shim is not proof that pre-TLS allocation was universally forbidden. Treat bootstrap failure as terminal under the selected root policy, not ordinary file EOF or a successful prepared table.
3. Record whether this boundary installed TLS itself; do not remove another owner's preexisting TLS. Keep it installed through all caller-side engine operations, future worker drain/join/destruction and cancellation completion. Eventual threadRemove must run on this same thread only after those uses stop. `PerThreadData.cpp:137–141` requires global removal after all relevant threads terminate. Runtime53's present infinite retained failure thread cannot be allowed to outlive global Foundation teardown merely because a shared_ptr remains alive.
4. Do not call Thread::attach just to satisfy this audit: PerThreadData TLS and Thread's identity slot are distinct. The inspected create/start/submit path needs no current Thread object. If later composition introduces an API requiring one, audit that concrete call then; creating another engine thread now is unnecessary.

The optional boundary provides per-thread Report flags and an ExitChain context; it does not repair profiler globals or establish recoverable engine failures. Its new Data/Gate allocations, failed TLS publication behavior and same-thread teardown must be reviewed before adoption. This audit closes the narrower question without altering callbacks, adding code or pretending native compilation proves allocation/thread behavior. The current source-only53 can still be compiled for syntax independently, but this audit does not approve its operational engine use or complete teardown.
