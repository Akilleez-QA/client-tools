# Blind review of frozen callback-composition46

Reviewed actual candidate source, run-portable-v1.py, freeze-v1.json, and raw evidence-v1 files before consulting any previous review or summary. No previous review/summary was consulted. No compiler, test binary, VM, vendor, engine, or product was run. Only this report was written. Findings concern this prototype and the portable evidence; they do not change or qualify product49d0's implementation. The raw result reports unchanged frozen inputs; I inspected the freeze manifest but did not independently recompute its hashes.

## Assessment

The portable composition is real within its stated boundary. Tests construct two independently retained service tables with different callback functions. SessionFileOwner passes context->services into FileInvocationJob::enqueueAdmitted; the explicitly substituted portable job constructs the actual MilesFileChannel26::Invocation with that table; actual Invocation dispatches through its retained service owner; selected_services dispatches through the retained native-style function-pointer table. This is materially stronger than directly calling adapter helpers. The compiled source list correctly includes portable_job.cpp instead of Windows FileInvocationJob.cpp. The latter was also inspected, but its Windows events, queued strong ownership, submit timing, and synchronization have no execution evidence here.

The raw build log is empty, results.json records successful build/run exits with ASan/UBSan configured, and run.log contains the expected scenario markers and 333 reported checks. The script makes its evidence directory exclusively and checks frozen input hashes before and after the attempt. These are credible records of the documented portable attempt, not independent reproduction or SDK/ABI evidence. Neither the marker total nor check total determines this review's assessment.

No blocking implementation defect was established in the reviewed, single-control-thread portable composition. The evidence supports distinct session selection, successful zero-handle admission, wide nonzero handle forwarding, preservation of tested noncanonical/high-bit status and negative seek bits, owner-level lifetime retention, and the tested return/ACK joins. It does not prove every semantic branch or every ownership edge.

## Concrete coverage findings

1. **P2 — Zero local handle forwarding has a false-pass gap.** `candidate/file-owner36/portable_job.cpp:12` makes table A return success status 7 with local handle zero. Subsequent read/seek/close requests in `candidate/callback-control45/tests.cpp:222`–244 establish that zero did not prevent creation and use of a wire binding. However, A's actual implementations (`portable_job.cpp:14`–16) ignore the received handle, and the test does not check it. A regression changing only zero to another local value on subsequent calls could pass. Table B explicitly checks `0x100000007` in every operation (`candidate/callback-composition46/selected_fixture.cpp:24`–30), so its pointer-width proof is materially stronger. Treat the current zero evidence as successful acceptance and lifecycle traversal, not an exact zero-value round trip. A future frozen test should assert A receives exactly zero on each operation.

2. **P2 — Status-zero failure/publication behavior is untested in this composition.** `Script36::openFails` exists but is never enabled by tests.cpp. The assertions at tests.cpp:214 verify status 7 and `0x80000001`, and the implementation branches on nonzero rather than exactly one. This usefully rejects boolean normalization and signed-positive-only success assumptions. It does not exercise zero status, a failed open that writes a nonzero local output, reservation retirement, or absence of a wire resource on failure. A regression that publishes a file for status zero would not be caught by this suite. Inspection of the present owner and encoding code shows the intended branch; it is source support rather than tested evidence.

3. **P2 if claimed as per-job ownership proof; otherwise a scope limitation — Lifetime probes do not isolate Invocation/job retention.** Tests.cpp:200–247 drops external callback-lifetime/context references and observes survival through ACK and close, then expiry at fixture teardown. Tests.cpp:251–266 repeats the survival check on a callback exception. This proves the composed session owner retains the callback lifetime while it remains alive. SessionFileOwner itself permanently retains `context`, which permanently retains `services`, which retains the table and lifetime. Consequently these weak-pointer checks still pass if a hypothetical job/Invocation implementation borrows table/context from that live owner instead of owning its own copy. Actual Invocation does own copies by source inspection. The suite does not independently demonstrate that ownership edge or queued-worker survival. The portable pending queue is weak, whereas the Windows job has an owning PendingContext; the portable test intentionally cannot validate that native queue contract. Fixture teardown after uncertainty is explicitly test-only and supplies no production quiescence/cleanup proof.

## What the ordering evidence establishes

- Forward-before-ACK retains a request pin until a real queued-reply ACK; ACK-before-forward leaves the command executing until its return observation.
- Two causal callbacks can be ACKed in reverse order without settling after the first ACK (`tests.cpp:269`–278). The coordinator's pending scan examines unacknowledged causal callbacks, not merely its contiguous ACK frontier.
- A second causal callback is admitted while the forward command is ReturnedWaiting (`tests.cpp:281`–290), and both ACKs are required before settlement.
- Background callbacks can remain pending independently of forward-command settlement. Stale/wrong/duplicate IDs and early/duplicate ACK observations fail the session with the tested ownership retained.
- These scenarios call ready()/pump() before observing the forward return. They test callback ACK ordering and arrival while waiting, not a forward return while the file job is still Pending, a concurrent callback/return race, or callback execution before enqueue returns. Those are additional schedules, not established failures of this implementation.
- Script36::pump() drains the global queue across fixtures. The two-session test is a useful same-process selection/correlation test; it is not evidence of independent scheduling or per-session worker execution.

## Scope boundaries

The native callback header is force-included through a Linux compatibility wrapper that erases __stdcall and supplies platform macros. The test explicitly requires a handle wider than uint32_t. This demonstrates tested Linux value preservation, not Windows/x86 calling convention or SDK binary compatibility. Authentication, fully validated forward replies/ACKs, actual Endpoint.send acceptance, and original TLS provenance are preconditions of the mapper API, not exercised transport guarantees. Failed-session retention depends on the documented outer-owner contract. No operational SDK path, vendor behavior, engine thread affinity, worker join, real-file cleanup, or product49d0 behavior is established by this portable evidence.
