# Assessment: reuse the possessed SDK's opaque nominal tags

Source-only hypothesis review requested by root. No change to51/60/67 or pipe sources, no compile/runtime, no SDK body publication. This changes65's design conclusion conditionally: **if the public nominal handle types are deliberately changed to the same global SDK tags, the direct native EOS/stream mapping is unnecessary.**65's mapping/timing obstacles apply to the current distinct nominal types; they are not inherent requirements of a direct native facade.

## Why the hypothesis works for the selected SDK

Possessed Mss.h2353/2357 names global struct _DIG_DRIVER and aliases its pointer as HDIGDRIVER;2361 does the same for _SAMPLE/HSAMPLE;5080 names _STREAM/HSTREAM. Windows MSS_STRUCT is struct (327–328). EOS2519 and stream callback5082 take those handle types with AILCALLBACK; setters4706/5190 return the same callback pointer types. These are declarations, not a reliance on copying struct layouts.

A future public header can forward-declare those three tags at global scope, then alias their pointer types inside ClientMiles. It must refer to `::_SAMPLE`, not declare a new ClientMiles::_SAMPLE. The existing __stdcall callback declarations would consequently take exactly the SDK pointer types. A private native TU should assert is_same for all three handles, both callback types and both registration signatures against the real header, in both include orders.

Then native register_EOS_callback and register_stream_callback can directly pass the callback and directly return the actual previous callback with no function-pointer casts, registry, trampoline or invented selection point. SDK synchronous/concurrent delivery and replacement timing remain the SDK's behavior because there is no adapter callback selection. An unknown prior native callback remains representable as the exact public callback type. The original native handle delivered by SDK is the same pointer identity returned by direct allocation/open. The code/state and SDK resource lifetime still belong to the caller/native contract; deleting the adapter map does not prove vendor quiescence or make callback exceptions safe.

## Costs and constraints

- The plain header becomes coupled to three selected vendor ABI tag spellings and their struct kind, even though it still includes no vendor header or layout. A later SDK using different tag names cannot be adopted without updating that deliberate contract.
- `_DIG_DRIVER`, `_SAMPLE`, `_STREAM` begin with underscore followed by uppercase: C++ reserves those identifiers to the implementation. The SDK already uses them as its platform interface. A hand-authored forward declaration relies on that selected vendor/compiler environment, not a portable ISO header claim. This should be documented and compile-checked, not obscured by spelling different tags (which would lose type identity). No broader reserved identifiers are needed.
- The SDK may later complete its own global types. A matching incomplete declaration is compatible; a second private completion with proxy fields would violate the design and risk ODR/layout conflicts. **Never define these vendor-tag bodies in the pipe backend.** Current public class names could remain aliases if needed, but their old `struct ClientMiles::Sample` definitions must then be moved, not redeclared under aliases.
- This is a public source/nominal-type revision and changes C++ mangled parameter/callback types. All participating objects must be rebuilt consistently; existing51/54/60/62 receipts cannot certify the revised header. Do not mix prior facade objects or present it as binary-compatible with distinct51 types.
- With identical types, SDK-aware code can interchange public/native handles more readily; the type system no longer distinguishes the two surfaces. The project must still select one backend for the entire session. Feeding a pipe token to the native SDK is invalid even though its pointer type matches.

## Pipe implication, with actual source anchor

plain-pipe61/candidate/PipeCore.cpp8–23 currently defines ClientMiles::DigitalDriver/Sample/OwnedStream proxy bodies, and its containers own those types. Under this hypothesis they become private PipeDriver/PipeSample/PipeStream objects in an implementation namespace. Public native-tag pointers are opaque identity tokens only; never allocate, dereference, delete or compute sizeof the SDK incomplete type in pipe code.

On the selected Windows pointer model, a proxy address can be converted to the opaque public pointer type for return/storage, with identity lookup against the authoritative private rows on ingress. A conservative implementation compares each registered row's generated public token and returns the already-owned private pointer; it need not dereference a pointer obtained by casting an arbitrary input back to a private proxy. This preserves stale/foreign/session checks before private object access. Keep proxy address stability/tombstone lifetime and borrowed-stream parent ownership from the existing pipe semantics. Do not introduce unproven generation encoding or pointer arithmetic. The actual Windows compiler/proxy conversion/equality path needs source review and scoped checks; this assessment is not a general cross-platform pointer-provenance guarantee.

Pipe EOS still requires its real registration/event/lifecycle implementation. Same-tag public declarations remove **native** type adaptation; they do not magically forward native callbacks through the helper. Existing pipe callback state should remain private and convert verified wire identities to the same public token Audio already stores.

## Recommendation to root

This hypothesis is materially simpler for the direct native reference than inventing registration maps solely to bridge nominal pointer types. Consider selecting it as an explicit next-version public-header policy after reviewing the narrow vendor-name coupling and consistent rebuild requirement. If selected, first author a separate header/type-check candidate plus direct native EOS/stream delegates and private pipe proxy rename/lookup diff. Do not alter frozen51/67 or silently reuse old compile receipts. Real runtime/quiescence acceptance remains needed for operational use, but it no longer blocks writing a faithful direct native registration wrapper: the wrapper delegates that behavior without interposing callback state.
