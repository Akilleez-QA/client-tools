# Callback reentry source review44

Source-only review of product HEAD `49d0eeed4ddaa177d7a93ea396c37c3d9b9942da`, file-executor29 extraction and file-executor33 worker. No compiler, test, VM, SDK runtime or product modification was performed. Paths below are relative to `/home/akilleez/Work`; line numbers refer to the inspected files. This is a bounded call-path audit, not a proof over arbitrary installed callbacks or every indirect call.

## Conclusion

No synchronous Miles call was identified in the canonical four file callbacks or the inspected TreeFile/FileStreamer/reporting implementations. Their intended work does not establish a need for arbitrary recursive Miles command execution. Use a pipe-specific, explicit unsupported-reentry guard before forwarding or blocking. Do not infer that reentry is impossible: virtual file operations, reporting observers and allocation/error machinery are indirect extension points. General recursive command pumping would add semantics and lifetime hazards not justified by these callers.

A concrete deadlock would be: original Miles command waits for its host file thunk; the client file worker executes that callback; an indirect callback path issues a synchronous pipe Miles command; that command waits for a host call thread still waiting for the original file reply. A separate host vendor worker does not by itself remove the dependency. No runtime deadlock was reproduced in this audit.

## Registration and lifetime

It registers all four non-null canonical functions after `AIL_startup` and before digital-driver setup. No null registration, table replacement, or reset-to-default call was found in that searched source.

This supports the current canonical install-once lifetime, not permission to silently ignore a different future public table. Installation must represent an actual owned table and actual backend registration. Preserve callback/table/file ownership through shutdown and any callback completion it requires. Absence of a null reset in game source does not prove the SDK never closes a file during shutdown or that external users cannot replace a table. Explicitly refuse unsupported transitions before vendor side effects; do not fabricate success.

## Recommended guard placement

Use client-side thread-local callback-invocation scope covering the selected service call on the admitted worker, with unwind-safe exit. This is distinct from host-callback-context41: that host scope carries causal provenance and cannot identify execution on the client file worker.

The first check should be at pipe facade `ClientMilesPipe::Session::selected()` entry, before reading `selectedSession`. In `stream-proxy37/overlay/backend-boundary24/pipe/ClientMilesPipe.cpp`, that global is at38 and selected()127–130; all inspected public forwarding operations obtain it. Reject callback-origin forwarding before inspecting proxies or session state, allocating command state, acquiring transport locks, enqueueing, sending or waiting. Checking only `Session::request`153 is too late for operations that inspect or mutate session/proxy state first; add a lower private ingress check there only as defense against internal bypass. Session creation/selection and any direct-channel entry must be covered or explicitly forbidden on callback workers as well. This recommendation does not claim existing selectedSession is thread-safe.

For the C++ client invocation boundary, a dedicated unsupported-reentry failure can unwind into the existing `Invocation::invokeOnAdmittedExecutor` catch boundary (`selected-file-services44/candidate/file-channel26/file_channel.cpp:137–181`); its CallThrew completion is not an observed SDK callback return and cannot be encoded as one. Ensure the owning session follows the unanswered/terminal failure path. Never convert this to read-zero/EOF, successful close or invented SDK status, and never allow a C++ exception to cross the actual original-DLL callback ABI. Host transport failure needs the already-designed nonreturning failure path. A callback that catches the guard exception still must not gain permission to forward; no command was sent.

The guard does not replace serialization of the canonical global map, worker TLS installation, or appropriate FileStreamer gate ownership. It should reject only forwarding from the selected file invocation; do not globally reject ordinary game-thread calls merely because another thread has an active callback. Likewise, TLS does not detect callbacks that create another thread and synchronously wait for it; no arbitrary cross-thread reentry guarantee is established here.

A targeted later test should install a selected callback that attempts facade forwarding, verify explicit failure before any channel interaction/session mutation, then verify scope cleanup on normal and exceptional exits. Include a normal game-thread call concurrent with a callback to catch a mistaken process-global guard. These are recommendations, not tests executed by this review.
