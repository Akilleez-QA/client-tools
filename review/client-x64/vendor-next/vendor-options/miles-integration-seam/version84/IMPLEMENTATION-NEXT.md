# Thin paired version implementation after probe84

Source-only recommendation; no new code or tests authored here. Keep public70 MSS_version(char*,int32_t), use the existing guarded/Core/Session path, and replace the historical fixed256 SessionVersion operation with one capacity-bearing request and one write-prefix reply. No new framework, generic buffer service or chunk protocol is justified for the observed Audio256 caller.

Use an explicit paired capacity limit of the existing reply payload budget (MilesStartup::ReplyTextLimit, presently MaxFrameBytes minus128). Accept each positive capacity up to that bound and pass that exact value to the private native resource operation. Reject null/nonpositive and above-budget calls through the existing private bridge-fault policy before sending or touching the caller buffer. Do not clamp capacity, truncate at256, or return fabricated empty output. This intentionally leaves positive capacities above the paired limit unsupported, while native70 itself remains unrestricted except for its positive/writable precondition. Document the limitation honestly rather than claiming complete public capacity-range equivalence. Allocate at most the accepted bound; allocation failure is a bridge fault, not a native version result.

Private host sequence: validate request/correlation/unused fields; preallocate scratch and reply capacity before the operation; acquire the module using the selected native DLL-name contract; on the macro's low-module outcome produce the genuine one-byte zero write; otherwise call the underlying ANSI resource API for resource1 with the exact requested capacity and capture its count. Release the acquired module in the private scope. Never substitute an already selected Backend module or expose SDK macro text in the packet/public header. This is a narrow private adaptation of the selected Windows macro, whose ignored count can now describe the write extent without becoming a new public status.

For the observed API behavior, encode count+1 actual bytes, including count0 plus its written NUL. Copy only that prefix into the caller after full response/context/extent validation and existing settlement. Caller tail remains untouched; do not read or send it. Use a bytes payload with explicit length, not an OwnedText scan/nonempty check, so resource content is not silently normalized. Check count is nonnegative and below the supplied capacity, returned prefix fits the payload, and its terminating byte is actually NUL. Initialize host scratch to a nonzero sentinel before the call so a future no-write count0 outcome is not mistaken for a zero initialized buffer. If the required observed write form is absent, fail as an unsupported private result form rather than manufacture a NUL or convert ordinary zero-count output into VersionQueryFailed. That fallback is a documented restriction outside the observed API behavior, not universal native equivalence.

No retry, second API call, version cache, whole-capacity transfer, maximum UTF16 expansion calculation or speculative2GB allocation is needed. The limit above deliberately avoids proving a universal code-page/resource bound. If later requirements include larger caller capacities, review that independently instead of silently changing this patch.

Keep pre-startup calls available within an established private session, as native70 does not require AIL_startup before its version call. Selected paired post-shutdown/session availability remains an explicit lifecycle limitation; do not hide it in the version result. Audio.cpp:2466 uses256 and is directly covered by the proposed range, but its successful operation still depends on the actual helper module/resource and integration. The own-resource probe is not evidence that the Miles module has a resource or loads successfully; low-load and zero-count responses are normal write-prefix outcomes under the selected contract.
