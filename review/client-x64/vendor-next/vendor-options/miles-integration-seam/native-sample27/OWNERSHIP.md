# Sample and input ownership

The public identity is `ClientMiles::OwnedSample*`, spelled HSAMPLE for the Miles-shaped operation subset. Only allocate_sample_handle produces it here. Copying the pointer aliases one allocation; it does not transfer or duplicate ownership. Only its selecting backend may interpret it. In this direct native candidate the value is the real SDK pointer behind a private cast, matching the existing native driver approach. A future pipe implementation must supply its own identity map and must never treat its proxy as a native Miles pointer. Stream-borrowed samples are not accepted or exposed by this extension.

The direct facade neither allocates a wrapper after the SDK allocation nor owns/copies/frees the supplied extension or file image. set_named_sample_file retains the exact existing pointer-plus-U32-size shape, signed block and raw signed result. It adds no inferred extent, unsigned narrowing, format recognition or fabricated result. sample_ms_position forwards both signed32 output pointers unchanged, including null; compilation establishes the pointer shape only, not which null combinations the actual runtime accepts. Values remain milliseconds.

The usage excerpt requires a complete image with its real signed positive size and an already-produced NUL-terminated extension. It does not reproduce SampleCacheEntry's unusual extension-selection algorithm or substitute a host filename. The caller keeps those bytes unchanged and alive throughout allocation, bind, query, end and release, including a normal failed bind. This conservative requirement avoids claiming an unmeasured early-release point for either input. The header's bounded format-detection minimum is not permission to shorten the actual audio image or evidence that the SDK copies it.

After a nonnull allocation the excerpt releases exactly once on both normal bind outcomes. On successful bind it preserves query→end→release; on failed bind it releases without pretending query/end occurred. This intentionally avoids the original helper's release-only-on-success leak. It does not prove cleanup if a future transport reports an uncertain side effect or if a vendor call fails to return. There is no destructor-triggered SDK call, automatic retry, device shutdown, ownership claim after driver destruction or cleanup policy for that unresolved case.

All five functions remain direct operations. No sample start, stop, EOS registration, streams, callback scheduling, image-transfer protocol or complete playback capability is added. Source and object checks cannot establish executable compatibility, vendor availability or fidelity.
