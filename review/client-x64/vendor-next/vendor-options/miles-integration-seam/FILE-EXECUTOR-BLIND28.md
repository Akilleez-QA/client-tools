# File executor: concrete integration at 49d0eeed4

Static source analysis only. No product edits, runtime tests, original DLL tests, or teardown rerun. Repository HEAD verified as `49d0eeed4ddaa177d7a93ea396c37c3d9b9942da`. Paths below are relative to that repository unless identified as seam candidates.

## Decision

The strongest minimal candidate is **one engine-owned executor for all file callbacks**, with known TLS ownership, serial execution and explicit engine lifetime. The inspected production-success file path supplies no concrete requirement to execute a causal request on the original game thread. Do not require a two-lane scheduler merely because FileStreamer uses TLS. Original-thread causal routing is a fallback if vendor dependency/reentry evidence demands it, or if exact diagnostic/fatal-context identity is required. One worker is viable under the conditions below; full DLL behavior remains unproved.

The TLS gate does **not** establish original-thread affinity: `sharedFile/.../FileStreamer.cpp:207–242` obtains the executing thread's gate, submits a request with a pointer to that invocation's stack result, waits, then closes that gate. Any correctly installed engine thread can do this, one outstanding read per thread. The file streamer remains a separate thread; never execute these callbacks on FileStreamerThread itself, which would wait for its own queue.

There is a concrete counterexample to *diagnostic*, not established production audio/data, equivalence: `TreeFile.cpp:687–691` reports and increments unexpected cache misses only on the main thread (non-production build). Moving a causal main-thread open suppresses that behavior. On fatal/error paths, ExitChain state/list are also per-thread (`ExitChain.cpp:64,80,117–153`), so moving a fatal path to a new thread changes cleanup context. This is a source distinction, not a claim that a particular DLL call triggers it.

`AbstractFile.cpp:52–55` calls its audio service hook before an entire-file read; `Audio.cpp:4944–4961` admits that service only on the main thread. Preserve this hook and the original thread of its resulting ClientMiles call. However, do **not** claim that ordinary file callbacks inevitably recurse through it: the inspected callback paths use `TreeFile::open`, `seek`, `read`, `close`; compressed Tree/TOC opens call FileStreamer::read directly (`TreeFile_SearchNode.cpp:478–497,842–862`). The observed entire-file hook in SearchCache belongs to cache population (`:900–918,1015–1016`), not normal SearchCache::open.

## Small patch sequence

1. **Extract the existing callback bodies inside Audio.cpp.** Keep TreeFile::open(name, PriorityAudioVideo, true), map, counter, seek switch/tell, signed-to-U32 read conversion, close/delete, and debug bookkeeping. Reuse the candidate `ClientAudioFileCallbacks` interface from `reverse-file-seam20`; make SDK trampolines and admitted pipe calls reach these same bodies. Local handle zero is valid on successful open (`s_nextFileHandle` starts at zero); success is the callback result, never handle truthiness. Keep local handles off the wire.

2. **Separate TLS ownership from the bodies.** Delete the process-global `once` dependency from the admitted engine execution path. `Thread.cpp:94–104` already installs TLS before `run()` and removes it afterward. Main-thread setup installs its own TLS (`PerThreadData.cpp:118–133`). Neither path calls threadInstall again. In particular, threadInstall(false) allocates a new Data/gate and overwrites the slot (`:189–211`); calling today's callback unchanged on a fresh engine worker does exactly that. Do not add an isThreadInstalled guard: its documented ExitChain-only purpose and legacy non-null TLS caveat remain (`:319–340`). Admission is based on known ownership, not a TLS probe. If native trampolines must still run on vendor-owned threads, isolate that separate legacy/registration policy; the engine executor must never inherit its once logic. This native-thread cleanup policy is not silently solved by the extraction.

3. **Reuse sharedThread for the background executor.** Follow FileStreamerThread's existing runNamedThread pattern (`FileStreamerThread.cpp:50–61`), with an owned queue, Semaphore notification, and ThreadHandle::waitZero at join. Create it on the installing game thread before callback registration at `Audio.cpp:1293`; publish readiness only from inside its run method, after Thread::threadFunc installed TLS. One request executes fully before the next. No TreeFile calls on the pipe reader. Do not register shutdown from inside this worker: ExitChain registration belongs to the caller's TLS list.

4. **Dispatch all admitted file requests to the worker first.** The receive side validates/owns bytes with file-channel26 and queues them; the worker invokes the original body and publishes its owned result. The concrete channel behind candidate ClientMilesPipe::Session::request must continue receiving/replying to reverse file messages while the original call waits; never block that receive progress on the ordinary response. Keep request/call/lease association for validation and lifetime even though it does not select the execution thread. Known causal requests and background requests share the same serialized file lane. Do not serialize the entire DLL operation onto this client file executor: a DLL call waiting for a file callback would deadlock it. A dependency where file-body execution reenters Miles would also need a different admission design; none is proved in the inspected success paths.

   **Fallback, only if required:** dispatch known synchronous callbacks to the waiting ClientMiles caller, and truly background callbacks to the worker. Hook causal pumping into the pipe call wait, not Audio::alter. Helper per-thread context around the actual DLL entry identifies same-thread causality; a process-global current-request label is wrong for vendor workers. Cross-thread causality cannot be inferred from timing. This fallback adds lifetime and two-executor locking complexity, so the debug-only cache-miss difference alone is insufficient justification for it.

5. **Serialize the shared bodies, not whole Miles calls.** The original s_fileMap/counter/debug containers are unsynchronized. Use one existing engine Mutex around each complete original callback operation, shared by any simultaneously reachable SDK trampolines and admitted pipe calls, including residual cleanup. If the selected pipe build truly admits all four bodies only on the worker, worker confinement supplies serialization; do not add a second scheduling framework merely to protect that map. Windows Mutex is a recursive CRITICAL_SECTION (`sharedSynchronization/.../Mutex.cpp`); same-thread nesting does not self-deadlock. Hold no queue, transport/session, or whole-ClientMiles-call lock while running the body or waiting for callback completion. The file-operation mutex can span FileStreamer::read because its worker does not acquire that mutex. Do not pump another file request while inside that gate wait: one TLS gate cannot distinguish overlapping reads. FIFO each lane; pin a binding through its operation; publish successful opens before replying; retire close only after its body returns. Reuse file-channel26 Invocation/completion ownership rather than inventing another value layer. Audit any new reentry path before allowing cross-thread nested dispatch while this mutex is held.

## Shutdown integration and blockers

Own shutdown explicitly from Audio/SetupClientAudio, not a separate later generic exit callback. `Audio::remove` stops sounds, then calls AIL_shutdown at :1437, then checks open handles at :1441; **all of those Miles calls can still need the callback service**. Enter a draining mode that stops new public work but retains callback admission for admitted calls and shutdown/background completion. Continue reverse-message processing during the shutdown wait; keep file execution and resources alive. Only after vendor callback production is known stopped, drain admitted invocations, resolve/close remaining local files through the original close body under the same serialization, stop/join the background worker, and release bindings/session. Do not replay a callback whose outcome is uncertain. Cleanup cannot delete a file or invocation still used by a local blocked read.

Audio's existing s_installed flag is insufficient for new lifecycle ownership: driver-open failure calls remove before s_installed is set (`:1314–1323` versus :1373), and the old shutdown block is gated by that flag. Track callback-executor readiness and vendor-startup ownership independently for partial-install unwind. Clear AbstractFile's service hook during final quiescence before deleting its Audio timer; the current remove leaves the hook installed, though serve normally no-ops after driver/timer clearing. Join before TreeFile search nodes, FileStreamer worker, and PerThreadData are removed. Confirm actual application installation/ExitChain order when implementing; do not infer safety solely from adding a callback with default priority.

The prior failed real Audio/ExitChain baseline is not evidence of success and is not authorized for rerun.
