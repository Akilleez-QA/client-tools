## Ticket lifetime and synchronization

- `invoke` serializes producers with `producer_`, publishes its stack Ticket and transaction before signaling work (130), and waits for done (132) before reading the result or leaving scope. The I/O owner waits for work before reading ticket (69–75), finishes request/reply writing before signaling reply (84), and touches transaction only after the producer signals consumed (87–89). It clears ticket_ and makes its last ticket access before signaling done (90–91). The producer cannot release the stack while the I/O owner still dereferences it. A next producer can acquire the mutex before the old stack's destructors complete, but those destructors only inspect Acked state/free independent vectors; they do not access shared FileTokens in that state.
- The auto-reset reply/consumed/done events each have one waiter and one handoff per serialized ticket. The manual-reset work event is reset after acquisition; no other producer can post the next ticket until the prior done and producer-mutex release. No lost-next-ticket sequence was found. Field visibility depends on the actual Windows SetEvent/successful-wait synchronization; the fields are not being treated as lock-free ISO C++ atomics. That Windows implementation/compiler behavior remains a future native/runtime acceptance item, not demonstrated by portable tests.
- The I/O thread holds no producer lock while awaiting consumption. Recursion detection precedes EnterCriticalSection. TLS origin snapshot precedes the producer wait and stays local; it does not read a different thread's active request. A reentrant same-thread invocation terminates before locking. Cross-thread SDK behavior remains an actual DLL acceptance question, not proof supplied by this review.
- Wait failure/timeouts take the nonreturning fatal route. They do not return while another thread retains a pointer to the producer's stack. fatal terminates/fail-fasts without intentional C++ unwind; its last fallback remains nonreturning. No retry is attempted after an uncertain transaction.

## Endpoint and ACK ordering

Endpoint construction, pump, send, receive and live storage stay on the dedicated I/O thread. The process-lifetime destructor policy does not transfer pending OVERLAPPED storage to a disappearing producer thread. The constructor's ready signal occurs after Endpoint construction. No command/SDK producer operates Endpoint.

The corrected synchronous partial-pump handling is present: send loops continue with no pending events while bytes remain; idle loop continues pumping; reply loop retries takeFrame after synchronous progress. Pending-event-only wait selection avoids spinning on completed manual-reset I/O events. Send completion is observed only when Endpoint has cleared its full write buffer, including partial completions.

ReplyTransaction validates the retained original request before token publication, read copy or close bookkeeping. Producer signals consumed only after successful consume. The I/O owner then obtains its prepared ACK, waits for the full write to complete, advances transaction to Acked, and signals done. The SDK result is unavailable before that state. ACK write completion does **not** claim client receive/consumption; the client50 independently validates and consumes it. For open, publishing the host token mapping precedes ACK; writing the SDK output pointer occurs after invoke returns, before the thunk returns to the SDK. No other SDK observer is promised that output before callback return.

Matched against client53 ordering: client preparation must finish before install send; installation callbacks can use an Executing admission; host returns from a callback only after ACK write, while client forward-return observation can still wait for its actual ACK receive. The independent client pump continues that join. A subsequent reverse request follows its predecessor's ACK on the same callback byte stream, allowing the client to publish an open before the host uses that token. No extra ACK table or acknowledgment of acknowledgment is required.

## Explicit integration limits, not newly found defects

There is no executable caller, both-pipe authentication, general Backend scope wiring or normal shutdown rendezvous in this candidate. The Runtime destructor is deliberately terminal. FileTokens lacks a completed-close/empty obligation query. Thus process exit, zero live tickets, ACK write completion and client reverse count cannot be substituted for stopped producers/all files closed. Client53 likewise retains failed/open ownership; neither half completes normal teardown yet.

Constructor allocation can throw before its body (notably FileTokens storage), and invoke preparation can throw before a ticket is sent. The actual SDK thunks catch invoke exceptions and terminate; the future command/bootstrap root must also contain Runtime construction failures before they could unwind through a live Backend emergency-shutdown destructor. The current source has no such caller, so this is a required composition boundary rather than a demonstrated current call-path regression. installAdmitted expects independently admitted origin and actual lifecycle state; its bool arguments do not themselves prove those facts.

The fixed30-second active deadlines introduce a terminal timeout policy and are not native filesystem equivalence. Long real TreeFile reads, SDK scheduling and selected callback behavior still need separately authorized acceptance; idle command silence itself has no deadline. No assertion here validates those timings, original DLL behavior, native thunk ABI compilation or Windows scheduling.
