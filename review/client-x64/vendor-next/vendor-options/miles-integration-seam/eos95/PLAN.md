# EOS95: proposed original-DLL registration diagnostic

Source inspection and prospective experiment only. No harness, compiler, vendor/audio/engine run, VM or product/Git change. No public EOS definition is added. This proposal deliberately does not repeat the completed generation or deferred-observer experiments.

## What is already known

Read actual ../miles-generation-live/probe.cpp and RESULTS.md: six original-DLL runs discriminate generation checks using a valid newly created handle, including two intended guard bypasses. Registration currently occurs only during CREATE, with one observer per resource; its return value is discarded. It does not test replacement/null registration. Six observed EOS entries were on foreign threads between commands. These records are contrary to assuming all EOS is causally nested in a forward operation.

Read ../miles-eos-observer/RESULTS.md and eos88/ASSESSMENT.md: immediate publication, maintenance-queued and unsolicited observer modes already distinguish delivery delays. There is no reason to rerun that matrix. Those results do not establish which registration an EOS producer selects during replacement or prove close/unregister quiescence. The available product Miles directory contains Mss.h; its typed registration declarations (:4706 and :5190) supply callback/return types, not a selection-time or termination guarantee. No additional possessed SDK timing documentation was located in that directory.

## Smallest discriminating matrix: six proposed processes

Reuse only the original diagnostic's pinned original x86 DLL, finite204ms asset, private isolated/null-sink routing and native v120 typed function declarations. Start a fresh process/driver/resource for each case. Two resource types (owned sample and stream), three cases each; one finite playback per process, no retries, no x64 controller and no game callbacks. The standalone x86 harness is sufficient: this experiment targets native registration, not IPC delay. Parent must review authored source, exact existing asset/DLL/tool identities, sink isolation and a fixed watchdog before any execution.

1. **Idle prior-pointer chain, then known selection.** Before START, set null and record the actual previous pointer (initial state is observed, not assumed). Then install A, replace with B, set null, set null again, install B, recording each typed previous return. After the first explicit null, expected previous values are exactly null,A,B,null,null in that order. Start once with B installed. Exactly B is the expected observer for normal single completion; A must not be selected. This directly discriminates returning the new pointer, a fixed thunk or stale pointer and proves null is actually forwarded, rather than merely maintaining a shadow client variable. Finish by null registration and record previous B. No invalid handle is used.

2. **Replace immediately after START returns.** Install A, START, immediately replace with B, recording entry/return QPC and thread ID around both operations and the returned A pointer. Do not sleep until a guessed percentage of playback or choose a schedule based on observed progress. A and B observers record their own callback identity/entry/exit independently of the current registration variable. Classify each callback against replacement begin/end, retaining overlaps and a callback that precedes replacement. A callback entering as A after replacement returned is a decisive observation of retained prior selection; B afterward is consistent with later selection but cannot prove when it was selected. If the timing window is not discriminated, report inconclusive rather than retrying until a desired result occurs.

3. **Null replacement while A is visibly active.** A's observer publishes ENTERED, then waits on a diagnostic event for a bounded interval; it never calls Miles, writes pipes or acquires a lock shared with the registration thread. A dedicated thread, started before playback, waits for ENTERED and calls null registration once, recording begin/end and previous-pointer result. The main thread releases A after a predeclared short hold (for example100ms) regardless of whether registration returned. Therefore the observer never waits for registration and cannot create a circular diagnostic dependency. Both sides have an outer watchdog. Record whether null registration returned before A's release or only afterward; either outcome is meaningful. The expected prior pointer is A. This tests in-flight callback exclusion under an intentional diagnostic pause; it does not show cancellation of callbacks not yet entered. Callback instrumentation changes timing and must be stated.

If callback entry fails to occur within the fixed playback/watchdog interval, preserve that failure/inconclusive result. Do not start another playback. On watchdog abort, retain all available records and terminate only the isolated diagnostic process; never invoke release/shutdown concurrently merely to force an unblocking result. Normal cleanup occurs only after the test's known observer exit and registration-thread completion, using valid resources. That cleanup is experimental hygiene, not proof of vendor producer termination.

## Minimal harness changes and independent oracle

Fork the diagnostic into a new private source artifact; retain original harness/evidence unchanged. Replace its CREATE-only observer binding with the three explicit scripts above. Add separate exact native sampleA/sampleB and streamA/streamB functions. Store callback pointer observations as typed comparisons mapped to labels NULL/A/B/OTHER, retaining raw diagnostic addresses privately. Never reinterpret one callback type as the other. Call the actual original-DLL registration function and record its real return; do not compute it from expected state.

Use preallocated bounded records and Interlocked event sequencing, plus QPC/thread ID/resource lifetime. Each record distinguishes command entry/return from callback entry/observer-last-work. No record is labeled vendor-stack exit merely because the observer is about to return. Callback paths must not wait on the logging mutex while registration holds it; no lock spans a vendor call. Record overflow, missing expected records, wrong typed previous return and extra playback are hard failures. A purely local postprocessor can validate synthetic records with wrong previous pointer, wrong selected callback, ambiguous overlap and callback-after-replacement cases before any vendor run; it must retain ambiguous timing rather than silently assign it to a command.

## Contract that can be implemented now, and what remains blocked

A narrow private registration owner can preallocate immutable typed callback records attached to existing resource generation, retain their code lifetime, reserve a session-wide registration ID, and return the previous *game* callback only after validated completion. Null is a real removal transition. A foreign previous native callback is not translatable; under exclusive helper ownership it must be null or the known typed helper binding. Do not publish working public registrations yet: these bookkeeping rules do not determine which record a concurrent native callback belongs to.

Operational replacement needs a defensible rule for callback selection relative to replacement. A fixed helper trampoline looking up the current registration at entry can misattribute a callback whose old function pointer was selected earlier. Cases2/3 can expose this mismatch or constrain an in-flight exclusion assumption. Six finite successful observations cannot prove the absence of a delayed old selection, producer quiescence, cancellation after null, or no callback after close. No amount of additional successful repetitions turns those into guarantees. If native documentation or a supported restriction cannot establish that boundary, retain the operational replacement/close limitation; do not solve it by unbounded retained tombstones or pretending the latest pointer is always correct. Delivery thread, lock semantics and close frontier from eos88 remain separate prerequisites.
