# Private upload authorization selected for93

This source-only candidate requires an explicit `uint32_t uploadBudgetBytes` at private `connectSession` and `Session` construction; there is no numeric default and no new public ClientMiles argument. The actual LiveChannel formats the value into its child command line; paired-bootstrap59/host.cpp strictly parses decimal digits with overflow rejection before constructing Backend. The parent-PID/nonce binding and private wire Version3 remain unchanged. This argument is trusted private-root policy, not an externally chosen wire allocation allowance.

Evidence does not justify deriving a default from a game cache cap. Product `src/engine/client/library/clientAudio/src/win32/Audio.h:155–156` has only commented-out max-cache declarations. Audio.cpp:117,364,1526,2499–2501 maintains/reports current bytes, not an enforced allocation limit. SoundTemplate.cpp:126–128 uses MemoryManager limits to choose sample variants; it does not authorize helper upload memory. A source-tree `rg --files` search found no WAV/MP3/OGG inventory from which to infer a largest shipped asset; this is not a claim about installed game archives. Explicit bootstrap configuration is consequently required for adoption. It is an implementation policy choice, not a missing human authorization.

Two independently owned N-byte contents are reserved against the same budget before allocating the first: the unchanged BufferUpload storage and unchanged copySealed output. The latter is constructed on Seal and kept in Backend until Release. `2*N` accounting uses uint64; eligibility uses division before multiplication. Budget must be >=2, input must be positive and <=budget/2, and the original Win32 contiguous signed pointer extent is checked. Host also checks the actual vector allocator's max_size before construction. The selected U32 aggregate policy admits at most INT32_MAX image bytes; this is a temporary implementation resource constraint, not a newly asserted Miles API maximum. Available address space/free memory is not proven by max_size; an allocation exception makes the private session terminal before any classification output.

Existing BufferUpload exposes no immutable vendor view. Reusing copySealed unchanged avoids adding a borrowing contract merely to save a copy. This deliberately retains two content owners; a later independently reviewed view/transfer change could reduce them. The byte budget counts content bytes, not vector/control-object overhead, allocator rounding or process RSS. Transport frame/Endpoint storage is separate and remains bounded by the existing MaxFrameBytes rules per frame. ChunkBytes is MaxFrameBytes-136 (1,048,440), not a whole-image cap. No cumulative image-count cap is introduced; a successfully retired transaction restores its content charge.

One staging transaction runs on the existing serialized command path. The caller must keep the source extent accessible and stable through synchronous chunking. Client precondition/size rejection sends nothing and never returns zero as a substitute. Once Begin is attempted, any exception/refusal in the whole transaction fails the client session and retains its transaction state; this is deliberately stricter than only postpublication refusal. Host retains upload state and forbids resume after any postpublication refusal or thrown upload operation. A known prepublication host refusal has no published image to retain. A received Release actually retires storage; an uncertain Release reply leaves the client terminal and does not undo that known host retirement.

The sole query is explicit-length readonly file_type. It calls the real SDK only after sealing and exact extent matching, retains storage through native return, preserves S32 bits including zero/failure values, then waits for confirmed Release before returning publicly. This lifetime decision applies only to this classification call. It supplies no proof of setter copy/retirement, WAV extent, engine callback quiescence, normal SessionClose, or operational game adoption. Invalid/untrusted image contents are not made safe for the vendor parser by span validation. SEH/process failure is not caught/proven by the C++ exception state guards.
