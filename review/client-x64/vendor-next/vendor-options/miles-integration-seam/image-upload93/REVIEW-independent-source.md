## Source-supported observations

* Public70 is unchanged: `int32_t file_type(const void*,uint32_t)`. The possessed SDK declaration is `S32 AILCALL AIL_file_type(void const FAR*,U32)`. Actual private Backend calls that declaration directly with the sealed vector and exact U32 extent. It memcpy-preserves S32 bits into return_bits, and Core uses signedValue only after classification and Release return successfully. Zero, negative and unknown classifications are not bridge statuses. The new guarded public delegate preserves the existing exception/reentry boundary.
* Explicit private budget reaches Session and host through the single LiveChannel constructor/child argument path. Decimal parsing rejects overflow and nondigits. Eligibility divides budget before doubling; 2*N is charged in uint64 before first allocation. BufferUpload and copySealed use the same vector byte type, so the sealed vector max_size check bounds both content allocations. Only one transaction can hold charge. This is content accounting, not RSS or allocator-overhead accounting; actual memory availability remains unproven.
* Backend reserves the existing Buffer identity before allocation/publication, owns BufferUpload and sealedImage as members, and checks exact kind/slot/generation plus resolved pointer before each operation. Buffer is already kind5 inside Coordinator's accepted Driver..File range; no missing coordinator-kind extension was found. Seal rejects repetition; classification requires exact declared extent, sealed copy size and not-yet-classified. Release closes/retires the registry generation before freeing either owner and clearing charge. Partial healthy release is allowed. No new callback/file registration registry is introduced.
* Allocation, copy or classifier C++ exceptions inside execute set terminal state; the real host heap-retains Backend and exits through its fatal path. A Seal allocation failure leaves the now-sealed first owner retained; it cannot safely resume but is not a lost buffer. A lost Begin reply can leave client uploadId unknown while the host still owns the published record; terminal session retention, not fabricated client identity or retry, handles that uncertainty. A lost Release reply can coexist with confirmed host retirement; the client suppresses the classification result rather than pretending storage remains live or retrying release.
* The client drives Begin/chunks/Seal/classify/Release on the existing command Endpoint. Added request payload reaches Channel and LiveChannel::exchange separately from the unchanged text argument. Exact per-phase resource checks precede inherited runtime.returned. Each transaction handle enters verifiedResources; no wire flag bypasses admission. The callback Endpoint still has its own existing dedicated owner.
* Ordinary host SDK operations while upload is active produce terminal refusal before dispatch. The separately routed file installer is explicitly blocked too. Invalid-resource refusals from the outer host path also call observeUploadRefusal, preserving the intended terminal policy. This is safe under the inherited serialized-caller contract, not evidence of newly thread-safe public calls; concurrent callers would still race existing Session/Endpoint state.

## Limits and review cautions

Positive nonnull extent, started Session, explicit private budget, at most budget/2 and original-host contiguous extent are stricter than the bare public/native function signature. Audio's observed call already checks installed, nonnull and positive int size, but that does not justify claiming complete native API-domain compatibility. Startup bootstrap still needs an explicit policy value; no product adoption is supplied.

The source must remain readable/stable throughout synchronous chunking; this provides no protection against concurrent caller mutation. Two full host content copies and per-frame transport allocations change time/memory behavior. Available Win32 address space, valid image contents and vendor parser safety are not proven by length validation. C++ catch guards do not prove SEH/process-fault recovery. Native retention/callback behavior, clean shutdown and engine interaction remain unmeasured.

The public handler deliberately withholds a native result until Release is confirmed. Consequently a transport fault after genuine classification terminates instead of returning the native result. This is an explicit private failure-policy difference, not a signed-result bug. A prepublication refusal may leave no host image, but the client still fails the entire transaction. Do not call this successful cleanup or normal teardown.

Version90 and image93 are both overlays of86 and touch common wrapper/Core/host/reply files. In particular image93's host encoder is still text-only, as its baseline requires. Blindly copying93 over a version90 composition would discard version's bytes forwarding and other changes. This is a future composition constraint, not a defect in the declared standalone93 overlay.

## Prospective tests and false-pass risks

1. Exercise actual execute (not only executeUpload) and the outer host admission/refusal path. Directly calling executeUpload bypasses terminal guards and ordinary-command/file-install exclusions. A component-only success cannot claim the full transaction path or host monotonic replay check.
2. Use actual BufferUpload/registry/codec/reply and fixed literal expected bytes for boundary, boundary+1 and multiframe inputs. Check exact payload-versus-text forwarding; a fake Channel that ignores payload could falsely pass sequencing counters. Use patterned reconstruction and byte-for-byte comparisons, not only chunk counts.
3. Test ordinary SDK call and file installation during an upload, unknown/stale resource refusal from the host's outer resolve branch, repeated Begin/Seal/classify, gap/overlap/empty chunk, and classification before full Seal. Confirm no supplier invocation on refusal and terminal no-resume behavior through execute.
4. Verify charge before first content allocation and two simultaneous owners at Seal, exact budget boundary/one over, max_size refusal, and restored charge after confirmed Release. A test of allows alone does not establish allocation ordering or ownership. Scripted component allocation failures must not become a real engine allocator workload.
5. Force same-slot reuse after Release and prove the old generation cannot resolve, release or alter the replacement. Hold the literal returned handle from the first Begin; a fabricated arbitrary stale handle could make the test vacuous.
6. Supply literal S32 bit patterns0,0xffffffff,0x80000000 and positive values. Check public return only after Release; dropped/malformed/refused Release must withhold it. Malformed Begin success and generic reply mutations must preserve outputs and fail before settlement. A rewritten validator or fake LiveChannel ordering cannot prove actual pre-return admission/ACK ordering.
7. Distinguish before-publication allocation failure, after-publication copy failure, classifier exception, lost Begin reply and lost Release reply. Check the actual retained members/registry/charge at each point; do not assert every failure retains a still-live host Buffer after a Release that really succeeded. Explicitly label SDK suppliers as substitutions with no vendor semantic evidence.

Future strict native objects must compile actual changed closure and BufferUpload TU, with genuine host AIL_file_type import and exact54 public delegates for standalone93. No such gate or portable execution occurred in this review.
