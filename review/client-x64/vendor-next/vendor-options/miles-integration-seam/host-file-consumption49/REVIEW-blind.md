# Blind source review — host-file-consumption49

Reviewed the four actual new source files, source.patch, the reused registry against its stream-native38 parent, actual file-channel decodeReply/copyRead, and the protocol48 ACK construction they invoke. No compilation, tests, SDK, VM, engine, endpoint or product execution. Only this review was written. A separately authored client dispatcher is not assumed connected.

**No blocking defect found under the stated single serialized callback-producer and lifetime preconditions.** This is source support for a proposed portable gate, not evidence that installation, dispatch or actual ACK I/O works.

Concrete checks:

- **Preparation/publication:** ReplyTransaction copies the Request, validates/encodes ACK storage and validates buffer/target shape before reserveOpen (`reply_transaction.cpp:10–30`). Open reservation is the final fallible preparation. reserveOpen performs registry allocation before changing the Record or incrementing lastToken (`file_tokens.cpp:20–26`). After successful reservation, the remaining constructor path cannot throw. publishOpen uses existing stable Record storage and registry publication without allocation; publication precedes exposing the token through result(). Registry storage growth cannot move the separately allocated Record array.
- **Reused registry delta:** Direct diff against stream-native38 shows only File added to the accepted reservation kinds. File follows the existing null-parent branch. Reservations remain non-resolvable until publication. Records are destroyed before registry, so outstanding Reservation destructors still have a live owner. No new slot-generation implementation was introduced.
- **Identity and reuse:** resolve first finds the monotonic SDK token, then resolves the independent host registry identity and checks the returned Record pointer. Client wire File identity is used only as remote identity. Close marks the host entry Closing before request exposure, so resolve stops accepting it. Successful close retires the host entry and clears the record. New reservations receive strictly increasing token numbers, including after cancellation or failed open; UINT32_MAX is checked before reserve. Reuse of a Record or host-registry slot cannot turn an old SDK token into a new live file. Successful open rejects duplicate remote identities among both Live and Closing records.
- **Reply validation and unknown effects:** consume sets Failed before any decode or mutation (`reply_transaction.cpp:46–66`). The actual decoder checks envelope kind/opcode, request/cause/lane/lease, status zero, forbidden fields, correct file-resource shape and exact read count/payload agreement. It does not interpret a malformed response as EOF or an ordinary failed open. Decode allocation exceptions remain Failed. Retrying consume cannot restore the transaction. Open publication failure retains the reservation; malformed close leaves Closing; result() stays unavailable.
- **Read and status semantics:** Source-bounded decode completes before copyRead. Destination capacity/nullness is checked both before send and before memcpy. Only the validated returned count is copied. The real decoder may allocate its owned read vector after send; that is not a claim of fully allocation-free reply consumption. Its failure is terminal and precedes destination copying. Nonzero open status bits and seek return bits are preserved as uint32_t without boolean normalization. Zero open status requires a null remote File and cancels the unused reservation; it returns token zero only after ACK write completion. Client-local zero handles are absent from this layer and are not reconstructed from host tokens.
- **Consumption/ACK ordering:** ack() is empty until open publication, failed-open cancellation, read copying, seek validation or confirmed-close retirement succeeds. Returned bits/token remain inaccessible until observeAckWriteComplete changes Consumed to Acked (`reply_transaction.cpp:68–77`). A missing/uncertain write leaves Consumed and no normal result. Local completed write is intentionally not represented as client-side ACK consumption. Actual write completion remains a trusted caller observation, not something this helper can infer.

The destructor contract is real and unusually strict: Prepared destruction cancels only unsent preparation; Issued, Consumed and Failed destruction call std::terminate before member destruction. Thus ordinary exception unwinding cannot silently cancel unknown opens or report a normal scalar return. consume called in the wrong state also becomes Failed. Acked/Cancelled can be destroyed normally. This is deliberate process-failure behavior, not recoverable cleanup; no test has established a future host failure boundary.

A later negative-test fixture must account for that contract explicitly. A stack-local transaction that intentionally consumes a malformed reply will terminate on scope exit; merely asserting false and continuing is not a valid ordinary test design. Use a separately reviewed retained-failure/death-test strategy, preserving required lifetime and evidence, rather than weakening the production destructor to make tests easy. Distinguish an uncertain ACK after known consumption from a malformed reply before consumption: the former may legitimately leave an open token Live or an already-confirmed close retired, while still withholding the callback result.

The helper does not lock the producer slot, own FileTokens/vendor destination lifetimes, authenticate registration/session facts, or verify that a reported write really completed. Those are explicit integration preconditions. FileTokens destruction supplies no remote closes or quiescence proof. No claim here connects a client dispatcher, validates x86 UINTa ABI, or enables operational SDK callbacks.
