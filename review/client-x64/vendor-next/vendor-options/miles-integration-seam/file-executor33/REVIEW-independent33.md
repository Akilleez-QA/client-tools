# Independent source review — file-executor33

**No concrete ownership, wakeup, or join-order defect found under the declared interface preconditions.** The worker/job split is source-consistent with the actual product Thread and Gate implementations. This establishes neither engine runtime safety nor a completed callback-owner integration.

Reviewed `EngineFileWorker.cpp/.h`, `FileInvocationJob.cpp/.h`, the adapter file-channel header and staged Invocation implementation, plus actual product `sharedThread/src/win32/Thread.cpp/.h` and `sharedSynchronization/src/win32/Gate.cpp`. Verified all ten candidate manifest hashes; reviewed worker/job files and adapter header exactly match their staged native inputs. No native, vendor, engine, or workload execution. Frozen inputs unchanged. Native object compilations are not treated as runtime proof.

- **Enqueue ownership:** the adapter constructs the job and PendingContext before submission, then releases its unique pointer before the worker can publish/run the callback. A true submit transfers context cleanup to adapter `execute`; false occurs before publication and lets the caller delete it. If execution finishes before submit returns, the enqueuer's local shared job owner still keeps State alive. Worker code never dereferences context after execute returns.
- **Queue/event ordering:** actual Gate uses a manual-reset event. Queue insertion and event open occur under the same mutex as dequeue/empty detection and event reset. A producer cannot insert between the worker's empty decision and reset. During stopping the event stays open; queued items drain FIFO and the empty worker exits. Execute runs outside the queue lock. Submit has allocation/short mutex costs, but does not wait for callback completion or pump nested work.
- **Thread ownership:** actual Thread starts with refcount one. `startOwned` adds the owner reference before native creation. Successful worker termination releases the initial self reference; owner release occurs only after `checkedJoin` observes native thread termination. Failed native creation leaves no executing thread and releases both references. Worker initialization makes the failed-start handle explicitly null. Used state prevents restarting an already attempted native start; allocation failure before used is set remains retryable.
- **TLS and teardown:** actual `threadFunc` installs PerThreadData before calling run, so the worker's ready event follows TLS installation. It removes PerThreadData after run returns, then releases the self reference and ends the native thread. Consequently successful handle join precedes owner destruction and follows TLS removal. Failed join retains the thread pointer, owner reference, and worker resources. Premature destroy aborts rather than silently freeing an active worker.
- **Job completion:** invocation results are written before SetEvent; status/poll/wait use the event before inspecting immutable completion state. Shared ownership must remain live while callers poll/wait or use the returned Invocation pointer, as documented. Completion signaling means adapter return, not file success: `Completion::state` still distinguishes CallThrew and invalid read count. No automatic replay, binding retirement, or successful-open publication is supplied here.
- **STL boundary:** engine code allocates/deletes its worker, Impl, thread subclass, and queue Item. Adapter code allocates/deletes PendingContext, State, Invocation and modern-STL shared owners. The exchanged payload is only `void*` plus a function pointer; engine code never performs typed deletion of adapter context. The private undefined Binding assignment declaration does not prevent needed copy construction or add cross-boundary ownership.

Preconditions remain material: owner lifecycle operations are serialized; intake is exposed only after Started; submitters are stopped before destruction; the receiver does not wait for jobs; Execute does not throw; required vendor production termination and close enqueueing precede drain. The worker cannot enforce external owner sequencing or prove vendor callback quiescence. Violating those preconditions is not a newly demonstrated implementation bug.

A wording detail does not affect correctness: `execute`'s queued shared owner is destroyed by its local unique_ptr during function epilogue, rather than literally after the callback returns. There are no subsequent context accesses in execute or the worker, so that timing is safe here.
