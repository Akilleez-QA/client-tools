## Identity correction and bounded hazard

The earlier blanket statement that71 retained existing tombstones was incorrect. PipeCore.cpp close_stream:467–472 erases the stream row; release_sample_handle:555–565 also erases the owned sample row. Published pointer tokens may therefore be reused by a later allocation. Post-release/post-close use is outside the native caller contract, so address reuse alone is not a fidelity defect for valid callers and does not justify permanent unbounded tombstones.

No implemented EOS queue currently delivers a valid callback to those freed rows: both EOS exports remain missing, and75 adds no EOS path. A future queued event retaining only a raw proxy address could create an asynchronous identity hazard after close/reuse; that must be addressed with existing session/wire generation/typed registration lifetime when EOS is implemented. No current valid queued-event failure is established.75 does NOT mutate row lifetime. A future discriminating EOS test should enqueue a valid old-generation event before close, complete the documented close barrier, open another stream, then ensure the old event cannot select it. Merely forcing an allocator to reuse an address or calling a closed handle would not prove a native-contract violation.
