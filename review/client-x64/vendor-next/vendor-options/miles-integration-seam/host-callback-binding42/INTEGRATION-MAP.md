# Minimal operational file-callback binding map

Read-only integration scout; no new scheduler implementation, compiler, SDK execution or product edits. Inputs inspected: current stream-native38 composed Backend/LiveChannel/Endpoint, sample-live31 host loop, native-startup25 callback typedefs, reverse-file-seam20 canonical service, file-channel26, current file-owner36 candidate and host-callback-context41. Owner36 is a candidate dependency, not an adopted live host component. No claim of an operational stream/file path follows.

## Concrete call flow

1. Client composition starts the real EngineFileWorker and retains engine/TLS lifetime, canonical file service/table and SessionFileOwner on one callback-control thread. It registers SessionFiles admission state before any file operation. Control-thread initialization must complete before the game-side set_file_callbacks request is sent. Worker Started means actual TLS-ready acknowledgement; coordinator registration alone is insufficient.
2. The unchanged public ClientMiles::set_file_callbacks(open,close,seek,read) retains the supplied four process-local callback pointers in a session-owned client table. It sends opaque registration identities using existing opcode28, never function addresses. The x86 Backend validates those identities/session lifecycle and installs four actual typed host thunks with ::AIL_set_file_callbacks. Only successful return commits Installed. There is no independent fileReady boolean. Host thunk-owner association must already exist during the actual SDK call, in case installation itself calls back.
3. The actual host call loop admits a command, creates hostcontext41 Scope from its own session incarnation/header/local admission ordinal, then calls Backend.execute inside that scope. Scope covers every SDK call including installation, stream open, serve and shutdown; refusal paths before vendor admission do not manufacture an origin.
4. Each x86 thunk obtains the immutable installed session binding, snapshots its own thread's context using that binding's session incarnation, and creates a reverse request. Ready gives causal wire request/lane/lease; Unsolicited gives causal0 with explicit unsolicited lane/lease rules. A vendor worker never inherits whichever command happens to be globally active. Mismatch/invalid snapshot is terminal binding failure. Fresh reverse request IDs are assigned by the session binding independently of the captured origin.
5. Client callback-control thread validates the authenticated callback endpoint/session, reverse monotonic identity and exact envelope, then maps any nonzero causal wire request to its retained admitted-command record and local coordinator admission. The host local ordinal is diagnostic provenance, not a wire authority token and not presumed equal to the client's ordinal. Only this mapper may construct owner36 TrustedAssociation; wire causal bits alone are insufficient. Unsolicited maps to admission0. It assigns the one-shot intake ordinal and calls owner.receive, owner.poll, then transmits owner.reply when ready.
6. Owner36 uses file26 and FileInvocationJob on the real admitted EngineFileWorker. No engine file call occurs on the pipe reader or arbitrary SDK worker. For supplied native-shaped callbacks, a small session-table service adapter converts open status+uintptr handle to OpenResult and back, preserving valid zero handles. Existing canonicalServices hardwires ClientAudioFileCallbacks; do not silently ignore the table passed to set_file_callbacks. Either compose the actual canonical table through that adapter or extend InvocationJob to receive the retained selected services. Native direct backend still forwards the four pointers unchanged.
7. Host validates the exact file26 reply against its own outstanding Request, copies requested read bytes into the original vendor buffer only after validation, or publishes a prepared file-token mapping for successful open. It sends an explicit consumption ACK after successful consumption; send completion alone is not consumption. Client routes that ACK to owner.acknowledge; it cannot retire records merely because it sent a reply. Host then returns the exact original callback result to the SDK. Close returns only after confirmed client close and consumption bookkeeping.

## Endpoint ownership and concurrency

Endpoint has mutable overlapped/buffer state and no synchronization. Never let host main loop and arbitrary callback threads call pump/takeFrame/send concurrently. A minimal host binding can serialize the entire reverse exchange under one callback mutex, with exactly one outstanding reverse request. It assigns sequence numbers under that mutex, performs callback Endpoint I/O itself, and releases only after reply validation/consumption ACK is sent. SDK callbacks may originate on different threads; each captures its own context before waiting. No SDK invocation is made while holding this callback-transport mutex. A per-thread reentry marker must reject same-thread recursion before locking, not deadlock on the mutex.

Current host receive(cmd,&cb), sent/drain helpers must change ownership accordingly: normal host command loop pumps only cmd after binding installation. Host callback channel's send/read/pump/drain lifecycle stays serialized through the binding. Cross-thread overlapped use must be checked in the native Endpoint gate (uses owned handles/OVERLAPPED, not a documented existing thread-safe contract). If this cannot be proved, one dedicated host I/O owner with a small pending-callback inbox is the fallback, not concurrent Endpoint access. Do not add general scheduling policy.

Client must continuously pump cb even when no forward command is in progress: a vendor worker may call back while the game is idle. Current LiveChannel.exchange pumps cb only during receive and explicitly rejects every callback frame, so simply replacing that assertion inside exchange is insufficient. One callback-control thread owns cb and owner36. Game call thread keeps cmd; it posts admission/start/end/install/drain records to the callback owner, waiting for publication of the admitted-command record before sending a forward command. All client coordinator/owner mutation occurs on that control thread. The EngineFileWorker remains a separate serialized engine executor. This is a concrete session I/O responsibility, not an application-visible backend or plugin interface.

Do not complete/remove the mirrored causal-command record until the actual forward reply and all causally admitted callback bookkeeping permit it. Existing SessionFiles request pins cover empty-resource stream-open admission. Background callbacks remain unsolicited even if a command is active. An idle poll loop or main-thread periodic Audio::serve is not a substitute for continuous reverse I/O.

## ABI, handle and failure obligations

Use actual Mss.h AIL_file_open_callback/AIL_file_close_callback/AIL_file_seek_callback/AIL_file_read_callback types with exact decltype/static_assert on x86; do not copy SDK declarations into a new public API. Native25 signatures use __stdcall, U32/open-result, UINTa handle and pointer, S32 seek, U32 read. Host UINTa is32-bit; client local handle is64-bit. Host must issue its own opaque32-bit file token, mapping to the wire File(kind,slot,generation); never truncate a client handle or send a pointer. Reserve host mapping storage before reverse open side effects, then publish allocation-free after successful reply. Client owner36 already reserves its own File record before invoking open. Confirmed close retires host mapping; uncertainty does not pretend close happened.

file26 already validates signed seek bits, open result independent of zero local key, read extents and complete association. Its current filename limit512 and read limit min(INT32_MAX,MaxFrameBytes-128) are real bridge limits. An excessive vendor request must fail the session explicitly, not be clamped/chunked without a proven equivalence contract, and not return EOF. Public stream37's larger filename-frame capacity does not remove file26's smaller callback-open bound.

The SDK callback ABI has no transport-failure alternative: close is void; open/read zero can mean ordinary file failure/EOF. A catch-all thunk boundary must therefore distinguish a validated normal callback result from transport/validation/owner/worker failure. It must never throw through the SDK and never return a fabricated scalar. On unrecoverable bridge failure the host must enter a nonreturning process-failure path (mark/log failure best-effort, terminate its owned process, with a guaranteed nonreturning fallback). Merely faulting a pipe then returning0 is wrong. No unwinding through Backend::~Backend is safe while the callback stack is active. Client observes channel uncertainty, retains operation/file/engine context and follows an explicit owner failure/termination protocol; process exit alone does not supply the missing per-file closes or consumption ACKs. Exact cleanup policy needs review before runtime.

Known client filesystem results are returned normally, including failed open or short/zero read. owner36 FailedUnanswered, malformed requests/replies, replay, callback recursion or impossible registration state do not have a legitimate SDK return representation. No helper require() throwing std::runtime_error may escape the thunk boundary. Allocation and OS errors inside callback handling belong to the same nonreturning failure path unless already represented by a genuine client callback result.

Replacing or clearing a callback table while streams/files exist is not covered by this first binding. Null SDK callback-table semantics and replacement lifetime must be established before supporting those calls; explicitly refuse unsupported registration transitions before any vendor action rather than inventing success/default file access. One installed table per dedicated host process is sufficient for the initial SWG installation flow. Retain binding and client service table through actual vendor shutdown/callback production end, outstanding replies/ACKs and worker drain/join. Coordinator zero pins alone is not proof of vendor termination.
