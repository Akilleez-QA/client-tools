## Verdict

The map is a sensible dependency plan, not an operational callback implementation. It correctly identifies most unsafe shortcuts. The smallest coherent next unit must include both endpoint owners, the selected callback table, registration, the reverse transaction/ACK, and explicit failure retention. Shipping four host thunks alone would introduce blocking behavior into a transport deliberately written for zero callbacks. No API64 library exists here; native header/type compilation cannot establish runtime fidelity.

## Blocking connection hazards

1. **Synchronous callback stalls the current forward exchange; idle callbacks are unserviced.** `stream-native38/private-source-v1/backend-boundary24/pipe/LiveChannel.cpp:84-98` sends a command, waits only for its forward reply, and then rejects any reverse frame. `live-bridge-candidate/common.h:25-35` pumps the callback endpoint but never dispatches its frame. A vendor invocation waiting for file I/O cannot produce the forward reply that releases this wait. The watchdog eventually converts the stall into failure. Between calls nothing pumps the client callback endpoint. This is known incomplete composition, not a defect in the existing no-callback fixture. Implement the independently running callback-control owner before enabling installation; replacing only the assertion is insufficient.

2. **The host loop cannot retain callback endpoint ownership after thunks begin using it.** `sample-live31/host.cpp:44-45,115` pumps/takes/drains `cb`; `stream-native38/private-source-v1/pipe-transport-candidate/endpoint.cpp:36-45,78-100` mutates shared vectors, counters, flags, and OVERLAPPED structures without synchronization. A worker thunk calling these while the main thread receives a command creates an actual C++ data race and can reuse storage still referenced by an outstanding operation. The map correctly requires exclusive ownership. Apply it to fault, cancel, destruction, and final drain too, not just ordinary send/receive. Do not hold the callback mutex across any SDK call. Capture each thread's origin before waiting for this mutex.

3. **ACK and forward completion require an explicit cross-channel join.** `file-owner36/candidate/session-file-admission34/coordinator.cpp:56-71` refuses completion while causal callbacks remain unacknowledged. `file-owner36/candidate/file-owner36/session_file_owner.cpp:126-137` releases operation ownership only on ACK. Host ACK write completion followed by a forward reply does not guarantee the client control thread has processed the ACK before the command thread observes its reply: these are different pipes/owners. Retain a command record containing both forward completion and callback settlement. On `PendingCallback`, keep pumping and retry completion after ACK processing; do not block the callback-control thread awaiting its own future ACK processing, and do not treat `PendingCallback` as a transport error. `sample-live31/host.cpp:90-94` is a fixture's immediate-completion pattern, not a template for this client-side join. The map states the retention goal but needs this concrete transition before implementation.

4. **Client-side callback reentry needs a stated boundary as well as the host recursion guard.** `file-executor33/EngineFileWorker.cpp:143-148` executes a supplied callback serially. `LiveChannel.cpp:84-98` implements synchronous forward calls. If an installed client callback itself enters a synchronous `ClientMiles` operation, the worker can wait for the host command loop while that loop is waiting for the worker's file reply. The host same-thread recursion marker proposed by the map does not detect this cross-process cycle. This is a conditional integration deadlock, not evidence that the existing canonical callback does reenter. For the initial scope, audit the actual four selected functions and define an explicit rejection of unsupported callback-origin forward entry before it waits. Do not solve this by adding general nested dispatch.

5. **Fixture idle timeout becomes an operational lifetime bug if copied unchanged.** `sample-live31/host.cpp:44` uses `common.h:25-35`, whose ten-second deadline applies even when waiting for the next ordinary command. A quiet game can therefore kill an otherwise healthy session. Continuous background callback support needs a stop/fault-aware idle wait; retain transaction deadlines separately. This is acceptable fixture behavior and an operational adoption blocker, not a discovered production regression.

## Semantics and ownership

- **The caller's four callbacks are not yet the dispatched services.** `file-executor33/FileInvocationJob.cpp:14-18` constructs every invocation with `canonicalServices()`, and `file-channel26/canonical_services.cpp:5-12` hardwires `ClientAudioFileCallbacks`. Merely retaining four pointers in Session would still silently ignore them. Add a retained selected-table adapter and pass its services into the invocation. Preserve the open status independently of the local handle, including valid zero handles. In contrast, `native-file-callbacks35/private-inputs-v1/seam/native-file-callbacks35/native_file_callbacks.cpp:24-27` forwards the four supplied pointers unchanged. Its assertions at lines 9-20 prove declaration/type agreement only.

- **Worker lifetime is an outer-owner obligation, not supplied by a shared context.** `file-owner36/candidate/file-owner36/session_file_owner.h:19-29` contains a worker reference, an opaque engine pin, and an explicit destruction prohibition. The owner destructor (`session_file_owner.cpp:38`) does nothing; `FileRecord` destruction at lines 12-15 destroys a Binding, not an engine file. On queued/open/uncertain operations, simply resetting SessionFileOwner loses file-close responsibility even if a queued job temporarily keeps its own result alive. `EngineFileWorker.cpp:62-66,152-167` requires explicit drain/join. This is documented incomplete lifecycle composition, not a broken destructor contract. Implement an outer owner that cannot release these objects until its termination/cleanup policy permits it. Host death does not synthesize missing closes or ACKs.

- **Pipe drain is cancellation, not file settlement.** `endpoint.cpp:102-116` cancels pending I/O and closes the handle; `LiveChannel.cpp:70-76` currently goes straight to pipe drain/process exit. That sequence cannot serve as the operational callback close protocol. Keep reverse I/O alive through actual SDK shutdown and its final callbacks; process/producer termination and worker join are separate observations. The emergency `Backend::~Backend` at `startup-bridge23/backend.h:34-40` invokes vendor shutdown during unwinding, so a callback transport exception must not reach it while already executing a vendor callback. The map's nonreturning host failure boundary is necessary.

- **Admission is not evidence of worker readiness or vendor quiescence.** `coordinator.cpp:84-94` registers bookkeeping only; `EngineFileWorker.cpp:87-91` is the actual post-TLS Started acknowledgment. `coordinator.cpp:95-110` intentionally records late callbacks even in Failed, while `readiness` at lines 134-145 counts pins. Those counters cannot prove that a vendor thread will never call again. Keep startup and producer-termination facts outside these counters.

- **Wire validation is useful but not a provenance mapper.** `file-channel26/file_channel.cpp:25-29,58-109,218-258` validates the expected association and result shape, and `copyRead` at lines 261-270 bounds the final copy. `TrustedAssociation`'s mapper remains only a forward declaration (`session_file_owner.h:8-17`). Implement authenticated-session correlation, replay prevention, and wire-request to local-admission mapping before constructing this authority. `host-callback-context41/call_context.cpp:23-28` correctly reports a thread with no scope as Unsolicited; do not replace that with a global active command. Pin the host binding before calling the SDK installer, but commit Installed only on its successful return.

## Minimal source-change order

1. Define one paired private protocol snapshot for installation identities, reverse correlation and consumption ACK; specify ACK lookup by retained reverse identity rather than trusting a client-local intake ordinal supplied by a peer. Preserve the existing public four-callback signature.
2. Add the selected-service adapter and session lifetime root, with worker Started as an explicit prerequisite. Keep worker and engine context retained through failure.
3. Implement the client callback owner and mapper, including continuous idle I/O, command publication before send, the forward-reply/ACK join, and ordered shutdown/failure states. Transfer all callback endpoint access out of LiveChannel's command thread.
4. Implement the narrow host binding: typed thunks, pre-reserved 32-bit host file tokens, per-thread origin capture, one serialized transaction, exact reply validation/copy/publication, ACK, and nonreturning terminal failure. Remove host main-loop access to `cb` and add Scope around actual vendor admission. Address callback-origin forward reentry explicitly.
5. Enable the installation transaction only once those owners compose. Remove fixture request tables and idle watchdog behavior in the new operational candidate, not in the retained evidence fixture. Then connect stream lifecycle to the installed binding and verify shutdown dependencies source-first.

These changes need no application-visible scheduler, plugin API, or alternate callback ABI. Keep the pipe machinery behind the same facade so eventual native64 linkage can remove the helper without changing callers. The current source does not establish original-DLL callback execution, arbitrary callback equivalence, engine runtime safety, or native64 availability; none is claimed by this review.
