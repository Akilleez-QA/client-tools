## Endpoint ownership decision

Use one command owner and one dedicated callback-I/O owner in each process. The client already needs an independently running callback-control thread for idle background I/O. On the host, use one narrow single-ticket handoff between thunks and a dedicated callback-I/O thread. No general work queue, RPC interface, nested dispatch, or policy scheduler is needed.

Why not have arbitrary SDK callback threads take turns operating Endpoint under a mutex? `endpoint.cpp:99-100` pumps both reading and writing; `common.h:44-47` uses pump while completing a send, so a callback can finish its ACK write with a read still pending. Mutual exclusion alone supplies no fixed issuing-thread lifetime for that pending operation. The dedicated owner avoids assuming an unproved cross-thread/issuing-thread-lifetime contract. Every send, takeFrame, pump, cancellation, drain and destruction of host `cb` stays on that one thread. This source observation is not a new claim of tested Windows behavior.

Keep `cmd` on the existing host command thread and client calling thread. Remove every `cb` reference from their receive/sent/drain paths after ownership transfer, including failure cleanup. The callback threads may signal terminal state through a small synchronized flag/event; they must never directly mutate another thread's Endpoint or client coordinator. Remove the fixture's idle ten-second receive watchdog for waiting between commands. Bound active transactions separately; command silence is not failure.

## Step 1 — private session root and client control loop

Add private `client_file_runtime.h/.cpp` beside `backend-boundary24/pipe/LiveChannel.cpp`. It owns the callback-control thread, callback Endpoint, one synchronized command-observation slot, Coordinator34, SessionFileOwner, Mapper45, and a bounded table of protocol48 FileAckExpected records keyed by reverse wire ID. It retains the actual EngineFileWorker owner, engine lifetime and selected callback code/state. The composition root passes the same runtime to Session and LiveChannel; this is private construction wiring, not another public backend API.

Move `callback_.reset(new Endpoint(...))` onto that control thread via transfer of the connected raw handle before any callback Endpoint I/O. Construct/start the actual EngineFileWorker and wait for Started (post-engine-TLS acknowledgment), then construct the service context/owner on the control thread. Post Prepared only after these are usable. The public installer provides the four pointers; the root supplies their existing engine/code lifetime pin. Do not invent a public fifth lifetime argument or use a global selected callback table.

Before the public installer supplies its table (the real startup call precedes installation), the control thread owns the coordinator but has no file owner/mapper yet. It admits/completes those pre-registration ordinary commands directly and refuses reverse-file traffic. Preparation constructs the file owner and mapper on that same existing coordinator, preserving the next local admission ordinal. Do not install a dummy canonical table just to construct the mapper early.

The control loop handles three specific inputs: admitted command publication/forward-return/stop observations; callback frames; completed file jobs. On a file frame, validate/decode to capture the exact FileAckExpected with the retained registration before calling mapper.receiveReverse, reserve its bounded tracking slot first, then queue the real job. Poll owner, send its stable reply, and call mapper.markReplyQueued only after Endpoint accepted the frame. On FileConsumptionAck, route by opcode before new-request monotonic checks, select the retained expectation by wire ID, validate the entire frame and authenticated session, then call mapper.acknowledgeConsumed exactly once. Release the expectation only after successful consumption. EOS CallbackAck cannot enter this path. Malformed/unknown ACKs poison the session without dropping uncertain records.

The callback owner continues pumping when the game sends no commands. It never waits synchronously for the EngineFileWorker: it polls immutable completion and services I/O/posted observations. Its stop path cannot join that worker while callbacks can still arrive.

## Step 3 — host single callback ticket and four thunks

Add private `host_file_callbacks.h/.cpp` alongside `startup-bridge23/backend.h`. Use actual Mss.h callback typedefs with exact x86 decltype/static_assert agreement for all four thunks. This unit contains immutable session/registration binding, a producer serialization mutex, a per-thread recursion marker, one callback ticket with request/reply/ACK-ready events, the dedicated callback-I/O owner, and a bounded host file-token table. It calls no engine APIs.

Each thunk follows this fixed order:

1. Enter its exception boundary and same-thread recursion check **before** acquiring producer serialization. Obtain the already published immutable binding; snapshot this SDK thread's Scope41 origin now. Ready preserves cause/lane/lease; Unsolicited uses cause0/background lane/lease0. Snapshot mismatch or recursion is terminal. Never read the command thread's currently active request as a substitute.
2. Acquire the single producer slot. Assign a fresh reverse request ID without wrapping; reserve required host-file token storage for open before sending anything. Validate bounds (filename including NUL <=512; read count within file26 limit) without clamping/chunking or inventing EOF. Prepare the entire retained request, expected reply context, ACK fields and output storage before side effects where possible.
3. Publish the owned ticket and signal the callback-I/O thread. The I/O thread alone sends the request and receives its full reply. It returns immutable reply storage to the waiting thunk; it must not hold the ticket-state lock while waiting on the thunk. All waits must also observe terminal failure.
4. The thunk validates against its exact original Request, then consumes the result on its own stack: for read copy validated bytes to the original vendor buffer; for open publish the pre-reserved opaque32-bit token mapped to the full wire File identity; for close retire its mapping only after a confirmed close result. Preserve uint32 open status independent of token (including client handle0), signed seek bits, and exact read count. Client uintptr values never appear as host handles.
5. Signal consumption/ACK-ready. The I/O owner sends the prepared protocol48 ACK and reports write completion/failure. Only after that completion may the thunk return its real callback result and release the producer slot. No SDK function is called while this serialization mutex is held. ACK write completion is not a fabricated client ACK observation; the client must receive/validate it itself.

Use nonzero monotonic host tokens with no reuse/wrap in this first bounded process lifetime, mapped independently of registry slot/generation. Exhaustion is terminal before another open side effect, not truncated handle reuse. A failed open publishes no mapping and returns its original zero status normally. Successful non-1 status remains unchanged.

Do not confuse protocol48's allocation-free ACK encoding with allocation-free Endpoint transmission: current `Endpoint::send` constructs a fresh vector (`endpoint.cpp:36-40`). Either retain this documented fallible send under the terminal-failure path, or add only a narrow validated swap-based owned-buffer send with storage prepared before the reverse transaction. Do not claim the encoder alone removed that allocation. Client reply copying similarly remains fallible after a callback; its owner must retain the result on send failure.

## Step 5 — failure and teardown are part of this patch, not destructor cleanup

Inside any SDK thunk, catch all C++ exceptions; any transport/shape/worker/reentry failure enters an explicitly nonreturning owned-host process failure routine. Best-effort failure signaling must not allocate or recurse into SDK; terminate the helper with a guaranteed nonreturning fallback if termination fails. No exception escapes the SDK callback and no fabricated zero/void return substitutes for an unknown outcome. Do not unwind into `Backend::~Backend`, which currently calls AIL_shutdown while started. Normal callback file errors and short/zero reads remain ordinary validated results.

Client control failure marks coordinator/session Failed, signals the waiting command and all control waiters, and retains callback table, files, jobs, ACK expectations and engine/worker context. Child death proves no further child callbacks; it does not supply missing file closes or ACKs. Do not let the current ordinary Session destructor silently dispose of this new runtime. The initial integration must provide an explicit retained failed-session owner or a defined process-fatal abandonment policy before any runtime gate; recovery/retry is not implied. Destruction with unresolved real-file ownership must not be advertised as clean close.

For normal shutdown, keep callback owners, table and worker alive throughout actual AIL_shutdown and all callback/ACK settlement. Only after proven callback producer termination, no outstanding tickets/results, file-close obligations and coordinator pins settled may the owners stop intake, drain/join EngineFileWorker, cancel/drain their own Endpoints, and release context. Replace `LiveChannel::finish` and host `drainSession(cmd,cb,...)` with that ordered private rendezvous. Drain means cancellation/handle cleanup, not consumption. Existing ten-second host exit wait may remain a bounded final process-exit check, not a shutdown dependency resolver.
