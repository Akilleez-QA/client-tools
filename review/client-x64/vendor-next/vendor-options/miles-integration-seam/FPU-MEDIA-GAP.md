# Floating-point environment: remaining media fidelity gap

**Preserving the original Miles DLL does not specify the floating-point environment in which the separate x86 host calls it.** This is a confirmed omission from the inspected host source, not a measured audio mismatch and not justification to force PC64. No execution, mode change, or new runtime gate was introduced by this review.

The product checkout HEAD is `49d0eeed4ddaa177d7a93ea396c37c3d9b9942da`. Its `Audio.cpp` calls `AIL_startup` at line 1289 and installs file callbacks immediately afterward. `Audio::alter` locks around queued `startSample` calls (2320–2337), calls `serve` later (2448), and directly calls controls such as `AIL_set_sample_3D_position` (2461, 2965). `Audio::lock/unLock` (4920–4929) simply forward to `AIL_lock/unlock`. `serve` conditionally invokes `AIL_serve` on the main thread (4946–4958); premix-buffer setters also call it directly (5119, 5126). None of these inspected boundaries establishes or records x87 CW/MXCSR. Locking does not itself establish a documented floating-point mode.

The inspected `sample-live31/host.cpp` enters its receive/admission loop and calls `backend.execute` without FP-state setup or capture. Its composed Backend/dispatcher and common support contain no explicit `fnstcw/fldcw`, MXCSR, controlfp/control87, or FloatingPointUnit policy. `alias-native36/host_composition.cpp` only anchors compilation of `Backend::execute`; it supplies neither a main routine nor additional FP policy. These facts leave host arithmetic context unmeasured; they do not prove the vendor never sets its own modes internally. The DLL is statically imported, so a record at main entry would already follow loader/import initialization.

The existing raw `msvc-b5bb8792/critical-review/dpvs-probe/fpu-runtime/trace/ground-transition.log` shows installation changing x87 `027f` to `007f`, then the first collision restore changing it to `037f` while the software precision enum remains PC24. This supports the known setter-state behavior and later PC64 main-thread observations. It does not record the original SWG→Miles startup, lock, control, or serve boundaries. Earlier standalone RPC observations of `027f/1f80` occur after initialization; they are neither untouched host startup defaults nor a measurement of original SWG Audio state. See the bounded prior review `parallel-review-next/codex-miles-fpu14-result.md` for that distinction.

Windows maintains machine-register context per thread ([Microsoft thread documentation](https://learn.microsoft.com/en-us/windows/win32/procthread/about-processes-and-threads)). x87 and SSE2 controls are distinct, and a combined controlfp result can be ambiguous when they differ ([Microsoft control-word documentation](https://learn.microsoft.com/en-us/cpp/c-runtime-library/reference/control87-controlfp-control87-2)). Neither fact establishes the initial state of an arbitrary Miles-created worker, what creation API/CRT it uses, or its internal mode changes. No inheritance rule is assumed here. A callback-entry measurement would describe that callback boundary, not the worker's entire mixing/codec interval. Synchronous calculations may depend on caller controls if the implementation uses affected arithmetic; no universal sensitivity or audible consequence follows from source omission alone.

The minimal next observation, if existing authorized diagnostics are later extended, is passive raw-state recording at matched boundaries:

- Original Win32 SWG: immediately before/after startup and driver open; before/after lock, the representative control/getter calls inside the locked interval, unlock, and serve. Separate pre-collision and post-collision observations.
- Host: earliest main entry, before/after actual startup and driver open, and immediately around corresponding real SDK calls—not only around encode/decode or whole dispatch. Do not label main entry “before DLL load.”
- Both paths: callback entry/exit on the actual callback thread, with thread ID, request/opcode or callback identity, raw x87 CW/status and MXCSR, captured into preallocated records before formatting or incidental FP work.

Keep rounding/masks/precision and sticky status flags distinguishable; retain the existing commands, asset, DLL identity and observer policy. First compare those observations. Do not transplant the x64 MXCSR representation into an x87 word, normalize every call to the collision trace's PC64, or force vendor-worker modes based on these source findings.
