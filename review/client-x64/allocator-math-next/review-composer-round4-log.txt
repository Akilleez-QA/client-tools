### 1. Client terrain (`clientTerrain`)

- **Producer/consumer:** Procedural terrain LOD uses a dedicated request thread, `Mutex` + `Gate`, and `stdmultimap<int, ChunkRequestInfo>` for pending work — keys are **`int` priorities**, not pointers; chunk metadata is value-type (`x`, `z`, `size`, `priority`).

	typedef stdvector<ChunkRequestInfo>::fwd ChunkRequestInfoList;
	typedef stdmultimap<int, ChunkRequestInfo>::fwd ChunkRequestInfoMap;

- **Lifetime:** Teardown waits on `m_requestThread` and clears maps (same design on Win32/x64; race paths are `DEBUG_FATAL`, not width-dependent).
- **On-disk / binary cache:** `ClientProceduralTerrainAppearance_Cache` / `ShaderCache` are in-memory GPU/material paths; environment data loads via **IFF** (`EnvironmentBlockManager.cpp`), not pointer-sized structs written raw to disk.
- **Excluded per your semantics:** D3D9 `getSortKey()` = `reinterpret_cast<int>(IDirect3DVertexBuffer9*)` (and terrain’s use of `getVertexBufferSortKey()`) — **preexisting batching order**, truncation/collision ≠ demonstrated correctness failure.

- **Win32 TCP IOCP:** `TcpClient::update` uses `unsigned long` for `completionKey` while `TcpServer` uses `ULONG_PTR`; both paths pass **completion key 0** into `CreateIoCompletionPort` and dispatch via **`OVERLAPPED*` → `OverlappedTcp*`**, so this is not a demonstrated x64 truncation bug (falls under known Windows/network review, not a new root cause here).

### 4. Remote pointers / callbacks
