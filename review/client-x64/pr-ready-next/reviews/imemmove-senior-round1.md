## C++ correctness and regression assessment

The old global overload accepts `int` and calls `memmove` with `uint`. With the VS2013 Windows x64 types, both conversion to `int` and conversion to 64-bit `size_t` are ordinary integral conversions; neither overload wins. A signed pointer difference also has no unique best conversion to those two lengths. The native baseline x64 log independently shows both failures: `Misc.h(233)` with argument type `uint`, and `probe.cpp(29)` with `ptrdiff_t`. This is a concrete compiler failure, not a hypothetical portability concern.

Renaming the wrapper to `imemmove` removes it from the CRT overload set. The explicit `size_t` cast is exactly the CRT parameter type. The function still returns the CRT destination pointer and still has the same two Debug pointer checks. Pointer expressions themselves are unchanged and remain pointers; this is a length-type correction, not a pointer-to-integer conversion. On Win32, `uint` and `size_t` give the same conversion of a valid nonnegative `int`; on x64 every valid nonnegative int length remains exactly representable in `size_t`. Negative lengths are not validated by either wrapper and must not be described as safe or equivalent invalid-input behavior.

All five changed expressions remain int-valued: `TCPVector::Size` at TCPQueue.cpp138/213, `lengthToEnd` and `lengthToEnd+size` at Iff.cpp621/623, and `bytesToCopy` at Md5.cpp119. The surrounding buffer arithmetic and counts were not edited. Iff's negative insertion/deletion delta is distinct from the resulting nonnegative move count required for a valid deletion. Nothing in this patch calls for changing that contract.

My tracked-source census agrees with the supplied first-party census: DirectInput's `sizeof` product and ImportImageDialog's `strlen+1` are size_t-valued CRT calls. DebugWindow's int-valued call is outside the shared-foundation include context. External STLport's `_algobase.h` pointer-difference calls remain CRT calls. On Win32, removal of the int overload can remove the engine Debug pointer assertions from those formerly int-matching calls, depending on lookup/include context. This is an acknowledged routing change; it does not undermine valid-buffer memmove semantics. I found no basis to claim that invalid-input diagnostics or all external consumers remain unchanged.

## Findings and bounded missing acceptance

1. **No blocking production defect found.** The diff repairs a demonstrated overload ambiguity and preserves the intended valid-input behavior of the renamed call sites. Debug runtime and gameplay behavior are not established by object compiles; no such claim should be made.
2. **Minor test-harness weakness: expected-failure classification is too broad.** run.py accepts any nonzero baseline-x64 build whose whole output contains both `C2668` and `memmove`. It does not require that these appear in the same diagnostic or reject additional unrelated compiler errors. Consequently a future broken baseline build could satisfy the control accidentally. The actual archived logs show the intended two memmove ambiguities, so this does not invalidate these observations. Tighten the diagnostic matcher and add safe parser fixtures if the tool is to provide durable automated discrimination. This is a tooling improvement, not a production blocker.
3. **Publication metadata needs synchronization.** RESULTS.md currently calls the tools uncommitted and identifies the candidate solely as `9eadbbb`; the reviewed HEAD commits the same tool bytes. Root stated it is updating this metadata. Before publishing, distinguish the production commit from the reviewed/test-tool HEAD. No native rerun is necessary merely to change these prose identities because the file hashes match.
4. **Missing acceptance is bounded to broader claims.** A genuinely initialized-engine Debug runtime check, changed-caller runtime scenarios, or a complete branch build would be needed to claim those integrations were tested. They are useful follow-up confidence, not mandatory new acceptance for this small source repair with unchanged valid-input operations. Similarly, binary hashes would improve forensic reproducibility; they are not necessary to understand the current narrow pass result.

The existing-output negative control records nonzero exit and an unchanged sentinel hash, consistent with `mkdir(..., exist_ok=False)` occurring before any compiler invocation. This validates fresh-output refusal. It does not test every runner failure path. No mutation control proving that a deliberately incorrect copy implementation fails is supplied, but the simple independent snapshot oracle is inspectable and sufficient for this scope.
