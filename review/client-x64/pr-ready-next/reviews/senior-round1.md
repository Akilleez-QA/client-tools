## ByteOrder

The implementation is appropriately narrow. The new `_M_X64` branch selects `_byteswap_ulong` for the long functions and `_byteswap_ushort` for the short functions, while leaving the x86 assembly body unchanged. `FoundationTypes.h` defines `ulong` as unsigned long and `ushort` as unsigned short; the probe asserts their 4/2-byte sizes. `ByteOrder.h` retains the existing `__cdecl` declarations and C++ linkage. No caller or data-layout change is introduced. There is no reason to widen these network values to pointer width or to migrate the Win32 path as part of this fix. Other architectures are not covered by `_M_X64`, and the draft correctly limits its claim to Windows x64.

The historical oracle is strong. It compares both directions to independent arithmetic/byte-derived expectations, exhausts 16-bit inputs, and includes 32-bit edges, individual/complement bits, each byte position, and a deterministic sample. It is not merely a round-trip identity test. The expected count is 166,631 input cases, each checking both conversion directions; it is not exhaustive 32-bit coverage.

I independently hashed the candidate ByteOrder.cpp: `84d6a070f6412908e2fb95cf4dfb9268478f9dc0be5b2fe4cd10f4b77b7a2f17`. It matches the historical v3 result and assembly-next source manifest. The relevant ByteOrder.h and FoundationTypes.h hashes also match that manifest. Historical raw results record passing Win32/x64 Debug/Release candidates, passing Win32 stock, failing x64 stock, and failing x64 no-swap mutants. The inspected x64 stock log fails on `naked`/`_asm`, and the inspected x64 map resolves all four named functions to `production.obj`. Those details establish genuine regression discrimination and production-symbol provenance for that historical build.

Boundary: identical source is not identical whole-checkout/build context. The historical response file includes outside SDK and `C:/swg-src` paths. I did not establish every included header's identity or rebuild the isolated head. The draft is accurate about this limitation. The required remedy is a self-contained compile/link/run recipe and a source/header identity manifest; then rerun the focused matrix when native testing is authorized. A full-client link is unnecessary to validate this function change. The existing non-identity mutation is enough to substantiate the oracle; four separate mutation families would be optional.

## Socket widths

The type changes follow the API boundaries correctly. `SOCK_ERROR` is a 32-bit operation result used by UdpSock's converted `recvfrom` return, and it should remain unchanged. `Sock` now initializes/stores/resets `INVALID_SOCKET` at socket width. Reviewed direct Sock and main UDP-library call sites pass these members to socket APIs without introducing a new narrowing temporary. TcpClient and TcpServer already store their sockets as SOCKET; their changed completion keys are pointer-sized output destinations, while the transferred-byte count remains an unsigned long. Both update loops pass `&completionKey` directly to GetQueuedCompletionStatus. The key is unused afterward, but its storage still must have the API-required width. No behavior change to the loops is warranted by this patch.

The global aliases remain compatible in the intended v120 Windows context; the repository's inspected projects request v120. Introducing `<stdint.h>` need not be treated as a regression against an unestablished pre-v120 compiler requirement. The Windows guards in both UDP headers preserve their existing non-Windows integer aliases. Updating both vendored copies avoids one obvious inconsistent declaration; it does not prove all binary consumers were rebuilt.

Independent identity check: every changed socket header in `next-build/socket-candidate.tar` is byte-identical to this candidate, including the public Sock forwarding header. The current/final source manifests likewise match Sock.h, both UdpLibrary.hpp files and TcpServer.cpp. They do **not** match this candidate's TcpClient.cpp: those manifests predate its completion-key edit. Therefore those older integration records must not be cited as validation of that final source file.

Raw `client-next-text.tar.gz` v3 results record 20 successful include-order/header-combination builds and runs. Stock results record ten passing x86 cases and ten failing amd64 builds. The inspected candidate run performs UDP loopback and checks a completion key with nonzero high bits. The later guarded IOCP probe records four successful Debug/Release Win32/x64 runs. These are useful historical checks of matching header declarations and SDK contracts. They do not execute Sock methods, store synthetic high bits through a real Sock object, or call either changed update function. In particular, real loopback socket handles need not have nonzero high bits, so loopback alone does not discriminate handle truncation; the compile-time layout assertion does.

The draft correctly discloses the lack of implementation execution. A blanket requirement for full network runtime integration would be disproportionate to these declaration changes. Prefer actual affected-TU compilation, a source-bound assertion for each completionKey edit, and an explicit rebuild statement. A bounded production UdpSock smoke test could increase confidence later, but is optional for this narrowly scoped submission. No such runtime was run during this review.

## PCRE count

The production change is correct and minimal. `maxSupportedCaptureCount = 10`, `subscriptCount = (10 + 1) * 3`, and `int captureData[subscriptCount]` are adjacent in PlayAnimation. Passing that same constant makes the argument an element count of 33 instead of the 132-byte size. The caller only tests `resultCode < 0` and never consumes individual captures. Keeping zero as a successful match therefore preserves the intended boolean filter when the capture output is too small. There is no need to reject expressions with more than ten groups, add a dynamic capture allocation, or change providers to correct this bug. The subject comes from the bounded pathBuffer/fgets path, so the nearby size_t-to-int subject-length conversion is not a concrete large-input bug in this flow.

The provider probe covers 0, 1, 10, 11 and 20 groups, expected return values, whole-match offsets, a no-match case, and adjacent sentinels. The curated ZIP's captured probe source matches the supplied count-probe.c after newline normalization. Raw results record six passing provider/configuration runs, and the inspected x64 Debug run reports 20 checks. This supports the corrected API behavior historically. It does not establish byte identity of the linked provider libraries to a fresh candidate build: their Windows paths are recorded, but I did not independently verify provider hashes from the examined packet. The repository header identifies PCRE 4.1.

The probe's sentinel check occurs after the successful match; the later no-match call is checked only for its return code. Adding a no-match sentinel recheck is a small optional improvement. Backreferences/optional or nested captures would broaden provider behavior coverage, but are not required to justify passing the correct capacity and should not turn this one-line fix into a provider qualification project.

Historical TU results show Win32 Debug/Release and x64 Debug compilation succeeded; **x64 Release says `metadata absent`**, not pass. The compiler runner uses an external copied scene file and reused PCH/tlog context; the examined archive does not establish the isolated parser source's identity. Consequently I do not credit those records as exact-head parser compilation. The PR draft avoids that overclaim. Its final submission should keep API-contract tests, parser compilation, and any future command-level test clearly separate, and include a source-bound regression check as described above.
